# ML 데이터·시뮬레이션 설계 기준 v0.2.0

작성: 2026-11-18 / 담당: 채연 / 상태: 담당자가 작성한 구현 기준 초안

이 문서는 현재 구현을 위한 설계 선택을 기록한다. 팀 전체가 여섯 특성의 모든 산식과 시뮬레이터 매개변수에 합의했다는 뜻은 아니다. 구체적인 팀 계약이 추가되면 차이를 기록하고 데이터·특성 버전을 올린다. 과거 보관 문서나 기존 코드의 임시 정의로 이 문서를 조용히 대체하지 않는다.

## 1. 출처와 확정 범위

- 사용자가 확인한 팀 합의: 호텔의 과거 장애율을 핵심 예측 신호로 삼는다.
- 팀장 지시: 가상 호텔 100개, 2025년, 과정 기반 예약 전달 누락·동기화 지연 오버부킹·미확인, D-1 호텔×체크인 날짜, 특성 6개, 0/1 정답과 미확인 제외, 4~9월 학습·10월 검증·11~12월 테스트, LightGBM과 규칙 비교, seed 42 및 코드·CSV·모델 인계.
- 아래 여섯 특성의 선택·산식, 시간, 집계, 라벨, 수치 범위, 평가 절차는 채연 담당 설계안이다. 관측된 현실 통계나 이미 검증된 모델 성능이 아니다.
- 기존 API-023의 `risk-features-0.1` 여섯 필드는 가상 예시다. 이번 계약은 `risk-features-0.2`로 구분한다. 기존 모델 파일이나 생성 CSV와 자동 호환된다고 가정하지 않는다.

## 2. 공통 식별자·시각·범위

- 호텔: `HOTEL-001`~`HOTEL-100`. 전부 `SIMULATED`. 내부 DB bigint와 외부 문자열 ID는 필요 시 별도 매핑한다.
- 이 실험의 목표 체크인 날짜 D: 2025-01-01~2025-12-31. 한 행은 `(hotelId, targetCheckInDate, asOf)`이며 중복을 허용하지 않는다.
- 예측 시각 t: D-1 09:00:00, `Asia/Seoul`(UTC+09:00). 모든 시각은 시간대가 있는 값이다.
- 집계용 달력 날짜는 한국 시각으로 정한다. 이벤트는 `occurred_at`과 모델/플랫폼이 사용할 수 있게 된 `available_at`을 별도로 기록한다.
- 시뮬레이션 시작: 2024-09-01. 2024년은 준비 이력이며 2025년 평가 표본에 섞지 않는다. 4월 1일 예측의 과거 90일 창은 2024-12-31까지 닿으므로 1월 1일부터 시작하지 않는다.
- 최대 숙박 4박, 증빙 수집 시도는 최종 숙박 결과 후 최대 7일. 마지막 체크인+최대 숙박일+최대 증빙 지연을 모두 포함하도록 종료 시각을 계산한다. 현재 설정에서는 2026-01-12 00:00:00+09:00까지 진행한다.
- 신규 예약 수요의 체크인 날짜는 2026-03-31(마지막 대상일+최대 리드타임 90일)까지 내부적으로 생성한다. 이는 연말의 향후 예약 유입과 1월 초 재고 경쟁을 자르지 않기 위한 buffer이며 2025년 평가 패널에는 넣지 않는다. 이 예약의 이벤트도 시뮬레이션 종료 시각까지만 처리하고 그 이후 미완료 결과는 평가하지 않는다.
- 2026년 YB-001 Mock 시연은 별도 고정 사례다. 그 응답을 2025년 학습 정답에 복제하지 않는다.

## 3. D-1 예측 대상 예약 집합

호텔 h, 날짜 D의 대상 집합 C(h,D,t)는 아래 조건을 모두 만족하는 예약이다.

1. 우리 플랫폼 예약이며 원호텔 h의 체크인 날짜가 D이다.
2. t까지 관측된 상태 이벤트로 재구성했을 때 공급사 계약이 CONFIRMED이다.
3. t까지 취소가 관측되지 않았다. 마지막 DB 상태를 과거로 소급 조회하지 않는다.

상태 재구성에는 `occurred_at <= t AND available_at <= t`인 이벤트만 사용한다. 늦게 수신한 과거 취소도 이전 스냅샷을 바꾸지 않는다. t 이후의 신규 예약은 실제 재고 경쟁에는 영향을 줄 수 있으나 이 행의 대상 집합에는 추가하지 않는다. 집합의 ID와 크기를 감사 자료로 고정 보존한다.

집합이 비면 `NOT_ELIGIBLE`, 정답 공란이다. 정상 0으로 채우지 않는다. 100×365=36,500은 달력 패널 크기이며 학습 가능 행 수를 보장하는 숫자가 아니다.

## 4. 여섯 특성 계약 — risk-features-0.2

순서는 아래 표와 스키마 파일에 고정한다. 이름·순서·자료형·산식·결측 정책이 변경되면 특성 버전을 변경한다.

| 순서 | 필드 | 정의 | 값의 범위·무관측 처리 |
| --- | --- | --- | --- |
| 1 | `pastFailureRate90d` | 과거 확인 완료 예약의 미제공률을 Beta(1,19)로 보정한 값 `(f + 1) / (n + 20)` | 0~1. n=0이면 사전값 0.05와 감사 표시 |
| 2 | `targetConfirmedBookingCount` | D-1에 고정한 대상 예약 집합의 예약 건수 `len(C)` | 0 이상의 정수. 객실 수가 아닌 예약 수 |
| 3 | `bookingVolumeGrowth7d` | 최근 7일 신규 확정 유입과 그 직전 28일의 주간 평균 비교: `(n7+1)/(n28/4+1)-1` | [-1,10]으로 clipping. 원값·건수 별도 보존 |
| 4 | `reconfirmationOverdueRate7d` | 최근 7일에 최초 호텔 확인 기한이 끝난 예약 중 기한 내 유효 회신을 관측하지 못한 예약 비율 | 0~1. 분모 0이면 0과 missing 표시 |
| 5 | `inventoryUnavailableRate7d` | 최근 7일의 동일 표준 조건 유효 판매 조회 중 판매 가능 객실이 1개 미만인 응답 비율 | 0~1. 분모 0이면 0과 missing 표시 |
| 6 | `isPeakDay` | D가 금·토 체크인, 7~8월, 또는 사전 고정한 가상 성수일 중 하나인지 | boolean. 캘린더 설정 버전 보존 |

### 4.1 과거 장애율의 분자·분모

- 날짜 창은 `[t의 한국 날짜 - 90일, t의 한국 날짜)`이며 과거 예약의 체크인 날짜로 판정한다.
- 분모 n은 그 호텔의 우리 플랫폼 예약 중 동일한 예약별 최종 정답 정의로 0/1이 확인됐고, 그 정답의 `label_available_at <= t`인 예약 수이다.
- 분자 f는 분모 중 최종 정답이 1인 예약 수이다. UNKNOWN·자발적 취소·노쇼·확인 미완료는 분모에서 제외한다.
- 예약별 비율이다. 과거 호텔·날짜별 OR 정답 비율과 섞지 않는다.
- 저장 필드명은 `pastFailureRate90d`이지만 입력값은 수축 추정값이다. 감사 자료에 `n_known`, `n_failed`, `raw_rate`(n=0이면 null), `prior_alpha=1`, `prior_beta=19`, `history_missing`을 보존한다.
- 0.05는 개발용 사전값이다. 현실 장애율 추정이나 이력이 없는 호텔의 정상 확인을 뜻하지 않는다. 테스트 결과를 보고 사전값을 다시 맞추지 않는다.

### 4.2 유입·재확인·판매 조회의 상세 기준

- 모든 이벤트 기반 특성은 `occurred_at`과 `available_at`이 t 이하인 이벤트만 사용한다. 최근 시간 창은 발생 시각 기준 `[t-window, t)`이다.
- `n7`: 호텔의 `[t-7일,t)` 신규 플랫폼 CONFIRMED 예약 이벤트 수. `n28`: `[t-35일,t-7일)`의 같은 이벤트 수. 공급사 재시도·중복 이벤트는 한 예약 한 건으로 센다. 이후 취소로 과거 유입을 소급 삭제하지 않는다.
- 재확인 기한: 플랫폼이 등록·발신한 최초 재확인 요청 시각+2시간. 응답 실패도 요청 발신으로 센다. 기한이 `[t-7일,t)`에 속하며 기한 당시 알려진 상태가 CONFIRMED이고 취소되지 않은 예약만 분모에 넣는다. 같은 예약의 재시도는 중복 집계하지 않는다.
- `available_at <= due_at`인 유효 호텔 회신이 없으면 기한 초과이다. 늦은 회신이 도착해도 당시 초과 이력을 지우지 않는다. 유효 회신은 요청의 예약·호텔·숙박일과 일치하고 스키마가 올바른 HTTP 200 날짜별 회신이다. AVAILABLE이어야만 유효한 것은 아니다. 202·404·503·타임아웃은 확인 완료 회신으로 세지 않는다.
- 판매 조회는 `(호텔 h, STANDARD, D 체크인/D+1 체크아웃, 성인2, 객실1, KRW)`로 통일한다. D를 다루는 7일 창 안의 조회만 쓴다. 유효 재고 수량 응답이 있는 조회만 분모에 넣고 202·404·503·타임아웃은 제외한다. 같은 요청 ID 중복은 한 건이다.
- 판매 조회는 공급사에 당시 보인 캐시 재고의 신호다. 시뮬레이터의 실제 남은 객실을 직접 읽지 않는다. 1박 상품의 판매 중단은 기존 확정 예약이나 전체 숙박의 미제공 증거가 아니다.
- 무관측을 뜻하는 0과 실제 관측 0을 구분할 수 있도록 유효 건수·missing 원인을 감사 자료에 남긴다. 감사 열은 모델 입력에 추가하지 않는다.
- `isPeakDay`는 사전 고정 캘린더로만 계산한다. 사후 수요나 정답을 보고 성수일을 역으로 지정하지 않는다. 현재 가상 성수일은 설정 파일에 있으며 공식 공휴일 통계로 주장하지 않는다.

### 4.3 선택 이유와 제외 필드

예약 수가 커지면 같은 예약별 장애율에서도 한 건 이상 실패할 가능성이 커진다. `targetConfirmedBookingCount`는 이 노출량을 설명한다. 가격 변동은 독립적인 가격 생성 기전이 필요한 간접 신호이므로 이번 여섯 개에서 제외한다.

호텔 ID, 시나리오명, 숨은 호텔 신뢰도, 실제 전달 누락 여부, 미래 재고·배정·회신·입실·사건·대체 예약·정답은 입력하지 않는다. 고객 이름은 Faker로 생성할 수 있지만 예측 입력과 정답 생성에는 사용하지 않는다.

## 5. 원예약 정답과 호텔·날짜 정답

### 5.1 예약별 정답

- `1`: 원예약의 필요한 숙박일 중 최소 하루가 최종적으로 이행되지 않았다는 검증 가능한 증빙이 수집됐다. 입실 시각+2시간을 복구 마감으로 정하고, 단순 지연·사전 의심만으로 확정하지 않는다.
- `0`: 원호텔이 원계약의 필요한 모든 숙박일을 제공한 결과가 확인됐다. 숙박 중인 미완료 예약은 0이 아니다.
- `UNKNOWN`: 원호텔 이행을 끝까지 확인하지 못함, 증빙 미수신·검증 미완료, 자발적 취소·노쇼 등으로 최종 원계약 이행 결과를 관측할 수 없음.
- 원호텔에서 적시에 복구해 원계약을 이행했으면 0이다. 원호텔이 미제공한 뒤 대체 호텔에서 해결됐다면 원예약 미제공 1은 유지한다.
- 공급사 CANCELLED, 호텔 404, 고객 주장, 503, Agent 분석 또는 위험 점수만으로 1을 만들지 않는다. 증빙은 가상 호텔의 최종 배정/거절/숙박 기록 등 원천 결과에서 발생한다.

### 5.2 호텔·체크인 날짜의 OR 집계

- 고정 대상 집합에 예약별 1이 한 건 이상 있으면 호텔·날짜 정답 `Y=1`이다. 다른 대상 예약의 UNKNOWN이 확인된 실패를 지우지 않는다.
- 집합이 비어 있지 않고 모든 대상 예약이 0일 때만 `Y=0`이다.
- 나머지는 `UNKNOWN`. 빈 집합은 별도 `NOT_ELIGIBLE`이다. 둘 다 CSV에는 감사 행을 남기고 지도학습·확인 라벨 성능 계산에서 제외한다.
- `label_available_at`: Y=1이면 첫 유효 미제공 증빙이 이용 가능해진 시각, Y=0이면 모든 대상 예약의 정상 결과가 이용 가능해진 시각의 최댓값이다. UNKNOWN에는 확정 시각을 꾸며 넣지 않는다.
- 같은 예약의 증빙 중복은 라벨 수를 늘리지 않는다. 기본 시뮬레이터의 최종 증빙은 실제 배정/거절에서 생성되며 거짓 최종 증빙·사후 의미 정정 시나리오는 이번 범위에서 생성하지 않는다. 정정 시나리오를 추가하려면 accepted/retracted 결과 버전과 각 asOf 당시 상태를 재구성하는 규칙을 새 버전에 정의한다. 나중의 정정으로 과거 특성을 소급 재작성하지 않는다.

## 6. 과정 기반 장애 시뮬레이션

### 6.1 상태와 사건

아래 흐름으로 이벤트를 생성한다. 최종 label을 특성의 가중합이나 Bernoulli 결과로 먼저 뽑고 그럴듯한 사건을 나중에 붙이지 않는다.

1. 호텔별 객실 수·고정된 전달/동기화/복구 품질, 날짜별 수요·계절성을 정한다. 숨은 품질은 입력에서 제외한다.
2. 우리 플랫폼과 다른 채널이 동일한 호텔·숙박일 재고를 두고 예약을 받는다. 공급사 캐시와 호텔 PMS 상태를 분리한다.
3. 플랫폼은 당시 캐시상 판매 가능하면 계약을 CONFIRMED로 만든다. 원예약 기간·인원·금액·ID를 고정한다.
4. 전송 작업에서 메시지 누락·지연·호텔 서비스 중단이 발생한다. 호텔이 메시지를 받으면 예약 등록·전 숙박일 확보를 시도한다. 누락은 호텔 미등록 상태를 만들지만 즉시 미제공 라벨을 만들지 않는다.
5. 다른 채널 예약·늦은 재고 갱신 때문에 캐시상 판매 가능과 실제 PMS 확보 가능이 달라질 수 있다. 플랫폼 계약 수는 객실 수를 초과할 수 있지만 실제 호텔의 객실 배정은 날짜별 물리 객실 수를 초과하지 않는다.
6. 재확인·고정된 수동 복구 절차가 누락을 발견하거나 수정한다. 객실이 있고 복구가 완료되면 정상 이행될 수 있다. 지연이 있어도 정상인 대조 사례를 포함한다.
7. 입실·숙박일 배정 시 최종 이행 또는 최종 거절이 일어난다. 거절 이유는 실제 상태 전이로 기록한다. 첫날만 실패하면 다른 날짜를 자동 실패 처리하지 않는다.
8. 결과 증빙의 전달·재시도·서비스 중단에 따라 관측 가능 시각이 정해진다. 증빙을 기한까지 확보하지 못하면 UNKNOWN이 된다. 완성된 truth를 독립 난수로 가려 UNKNOWN을 만들지 않는다.

### 6.2 기본 가정

- 한 호텔에 STANDARD 객실 상품 하나, 성인2·객실1, 숙박 1~4박. 통화 KRW, 금액은 음이 아닌 정수이다.
- 예약 요청 시각은 체크인 날짜-리드타임 날짜의 00:00:00~23:59:59 사이 균등한 초로 생성한다. 리드타임 1일 예약도 D-1 09시 이전/이후로 나뉘며 대상 집합에는 당시 알려진 예약만 들어간다.
- PMS 예약 확보와 실제 숙박일 배정은 모든 필요한 밤을 원자적으로 검사한다. 보호된 PMS 예약을 다른 고객에게 중복 배정하지 않는다. 체크아웃 날짜는 재고 소비에서 제외한다.
- 플랫폼도 확정 시 캐시의 모든 요청 숙박일을 원자적으로 검사·차감한다. 캐시 갱신은 그 시점의 PMS 여유 스냅샷으로 교체하며, PMS가 모르는 누락/미처리 계약의 차감분은 이 단순 갱신에서 복원될 수 있다. 이것과 다른 채널의 새 확보가 초과 계약의 원인이다. 단순히 한 채널에서 차감 없이 계속 파는 버그를 장애 기전으로 삼지 않는다.
- 다른 채널은 PMS의 실제 여유를 확인하고 확보 성공 시만 확정한다. 플랫폼은 지연된 캐시 때문에 초과 계약을 만들 수 있다.
- 동일 예약·전달 메시지 ID의 PMS ACK/재시도는 기존 확보 결과를 반환하며 객실을 재차 차감하지 않는다. 취소 시 확보된 PMS 재고는 한 번만 해제한다. 플랫폼 캐시의 취소 복원은 취소 알림 시점에 한 번만 하되 이미 반영한 PMS 갱신과 이중 합산하지 않고 최신 PMS 스냅샷으로 재계산한다.
- 입실 시각은 체크인 날짜 15:00 + 사전 생성한 0~4시간의 도착 지연. PMS 확보 예약을 우선 보호하고, 미등록 예약은 실제 도착 시각·예약 생성 시각·ID 순으로 복구/배정한다. 모든 채널에 같은 명시적 우선 정책을 적용한다.
- 자발적 취소·노쇼는 별도 사건이다. 최종 계약 상태를 그대로 학습 정답으로 치환하지 않는다.
- 전 기간의 원자적 확보가 거절되면 실제 부족한 숙박일 중 가장 이른 날을 blocking night로 기록한다. 최종 복구 마감까지 실패한 경우 그 날의 미제공 증빙과 원예약 실패 1을 남긴다. 시도하지 않은 다른 숙박일은 UNKNOWN/NOT_ATTEMPTED로 남기며 모두 미제공으로 만들지 않는다. 기본 버전은 최종 거절 후 원예약의 후속 숙박일을 다시 시도하지 않는다.
- 호텔별 성향은 기간에 걸쳐 지속되고 별도의 일시 장애도 발생한다. 과거 이행 경험이 미래 전달·동기화·복구 품질과 자연스럽게 연결되도록 한다. 중요도 순위를 강제하는 라벨 규칙은 두지 않는다.

### 6.3 복구·관측 정책

- 예측 대상일 D에 대한 기본 재확인은 D-1 10:00에 제출한다. 그 뒤 새로 확정된 예약은 확정 직후 제출한다. 기한은 2시간이다.
- 전달 작업의 명시적 오류는 +1시간·+6시간·+24시간에 같은 메시지 ID로 재시도한다. 유실로 오류가 관측되지 않은 경우 재확인 과정에서 미등록 사실이 발견될 수 있다.
- 기한 초과·예약 미조회 시 운영자의 수동 확인 대기열에 들어간다. 호텔별 일일 처리 한도 3건, 매일 16:00 처리, 미완료는 다음 날로 이월한다. 복구 완료 시간은 처리를 시작한 시각 뒤 1~24시간 가상 지연과 호텔 상태에 의해 정한다. 접촉에 실패하면 같은 작업을 다음 날로 이월하며 복구 마감 이후에는 종료한다.
- 지연 전송·재시도·수동 처리의 실행 직전에 현재 생명주기를 다시 검사한다. 취소·노쇼·최종 실패 상태에는 새 객실을 확보하지 않는다. 기존 확보분 해제는 한 번만 한다. 입실+2시간 이내 복구만 최종 결과를 정상으로 구제할 수 있고, 이후 늦은 작업으로 이미 확정된 실패를 뒤집지 않는다. 늦게 도착한 증빙의 수집은 별도 허용한다.
- 모델은 시뮬레이터의 복구 순서·처리량·라벨을 변경하지 않는다. 모든 후보 모델은 동일한 고정 운영 정책 아래 생긴 결과로 비교한다. 이 실험은 AI 개입의 인과적 개선 효과나 무개입 위험을 측정하는 실험이 아니다.
- 정상 증빙은 전체 숙박 종료 후, 실패 증빙은 최종 거절 후 생성한다. 관측 수집기는 증빙 생성 후 2시간부터 시작하고, 실패 시 6시간 간격으로 최대 7일 시도한다. 호텔 서비스/증빙 전송 작업이 복구되지 않으면 미확인으로 남긴다.
- `evidence_delivery_drop_probability`는 수집 재시도마다 라벨을 가리는 확률이 아니다. 실제 숙박 결과 시점에 생성하는 증빙 발행 작업이 outbox/로그 기록 장애로 유실되는 확률이다. 유실 사건과 작업 상태를 기록하며, 원천에 증빙이 만들어지지 않아 후속 조회로도 얻지 못하면 기한 후 UNKNOWN이다. 생성된 증빙의 단기 서비스 장애는 재시도로 복구될 수 있다. 숨은 truth 파일로 관측 증빙을 보충하지 않는다.
- 시뮬레이터 truth와 관측 증빙은 별도 저장한다. 지도학습 CSV 라벨에는 관측 증빙만 사용한다.

### 6.4 수치 범위의 성격

객실 수, 예약 유입량, 전달 누락률, 지연·동기화 주기, 서비스 장애와 복구 확률은 `simulator_v0.2.json`의 가상 매개변수다. 실제 호텔·플랫폼의 추정 통계가 아니다. seed 42의 학습/준비 구간 파일럿에서 수치·클래스·관측 가능성을 확인하고, 테스트를 열기 전에 고정한다.

두 클래스가 부족하면 임의 라벨을 주입하거나 테스트를 보고 장애율을 조정하지 않는다. 데이터 생성 조건 자체를 새 버전으로 수정하고 이유와 변경을 기록한다. 수정 후 전체 데이터를 다시 생성하며 이전 성능과 구분한다.

## 7. 학습·검증·평가

- 2025-01~03월: 이력 준비/감사. 04-01~09-30: 학습, 10-01~10-31: 검증, 11-01~12-31: 테스트. 날짜 배정은 체크인 D로 한다.
- 학습 라벨은 첫 검증 예측 시각인 2025-09-30 09:00+09:00 **이전**, 검증 라벨은 첫 테스트 예측 시각인 2025-10-31 09:00+09:00 **이전**에 확정되어야 한다. 경계와 같아도 보수적으로 제거한다. 테스트 라벨은 고정 추출 시각까지 수신된 결과만 사용한다.
- UNKNOWN·NOT_ELIGIBLE·경계 제거 사유를 `split_audit`에 기록한다. 달력 구간의 이론상 행 수 18,300/3,100/6,100과 실제 포함 행 수를 구분한다.
- 같은 호텔이 기간에 걸쳐 반복된다. 이 분할은 이후 시기의 같은 호텔 예측을 평가하며 처음 보는 호텔의 일반화 평가로 설명하지 않는다.
- 주 비교 규칙: `ruleScore = 1 - (1 - pastFailureRate90d) ** targetConfirmedBookingCount`. 예약 독립 가정의 노출량 보정 점수이며 보정된 확률로 표시하지 않는다. 과거율만 쓴 점수도 참고 기준선으로 별도 보고한다.
- LightGBM은 동일한 여섯 특성을 사용한다. 호텔 ID·감사 열은 입력하지 않는다. 탐색 후보는 num_leaves {7,15,31} × min_child_samples {30,100}, learning_rate 0.03, 최대 2,000회, early stopping 50, seed 42로 제한한다. 검증 AP를 우선하고 동률이면 단순한 모델을 선택한다.
- 인계할 모델은 4~9월 학습과 10월 검증으로 선택한 checkpoint이다. 이 버전에서는 학습+검증 재학습을 하지 않는다. 추후 재학습은 모델 버전·라벨 가용 시점·평가 범위를 새로 기록한다.
- 데이터의 가상 사건·특성 정의·기준선·탐색 범위는 테스트를 열기 전에 고정한다. 검증 구간에서 선택한 각 모델의 F1 최대 임계값을 동결하고, 동률이면 높은 precision, 다시 동률이면 높은 임계값을 택한다. 운영 선별 임계값은 별도 Spring 정책이다.
- 테스트에서 Average Precision(PR-AUC 표기 시 AP 방식 명시), ROC-AUC, precision/recall/F1, 혼동행렬, 양성률, 표본 수를 함께 보고한다. 한 클래스만 존재하면 정의되지 않는 지표는 null과 사유를 남긴다.
- 일일 상위 K=10은 가상 검토 예산이다. 전체 적격 대기열을 점수 내림차순·동점 호텔 ID순으로 정렬한 뒤 K개를 선정한다. 미확인 행이 차지한 위치도 유지한다.
- 상위 K의 확인 라벨 성능과 전체 선택 수·확인된 선택 수·UNKNOWN 선택 수를 함께 보고한다. precision 하한 `확인된 TP/전체 선택`, 상한 `(확인된 TP+UNKNOWN 선택)/전체 선택`, 확인된 양성에 대한 recall을 구분한다. UNKNOWN을 분모에서 몰래 제거한 성능만 제시하지 않는다.
- 호텔 규모·대상 예약 수·장애 원인·월·관측률 구간별 성능과 라벨 관측률을 점검한다. 관측이 어려운 호텔이 빠진 선택 편향을 공개한다.
- 과거 장애율의 중요도는 검증 구간 permutation importance와 해당 특성을 제거한 비교로 확인한다. 1위가 아니면 결과 그대로 기록한다. 순위를 맞추기 위해 테스트 결과에 맞춰 라벨·특성을 수정하지 않는다.

## 8. 재현성·산출물

- 주 seed=42. 호텔/전달/수요/관측/Faker 등 목적별 RNG를 안정적인 component ID로 분리한다. Python 프로세스별 `hash()`를 seed에 쓰지 않는다.
- 이벤트 동시각 정렬 우선순위: 해제/취소 → 서비스 상태 → 예약/전달 → 조회/증빙 수신 → 예측 스냅샷 → 입실/배정. 동일 종류는 안정적인 event ID순이다. 도착/배정이 실제 시각보다 앞서지 않게 한다.
- 학습은 단일 스레드·LightGBM deterministic 설정을 기록한다. 라이브러리와 설정 버전, 데이터 SHA-256, 소스 커밋, 특성 순서, 모델 버전, 시나리오 수를 manifest에 기록한다.
- 원천 이벤트/예약/숙박일/관측 증빙, 숨은 truth 감사 자료, 특성·라벨·train/validation/test CSV, split audit, 품질 보고서, 모델 파일·메타데이터·평가 보고서를 구분해 저장한다.
- 모델 입력은 스키마의 여섯 필드만 선택한다. JSON/CSV 전체 열 자동 학습을 금지한다. 감사 열을 모델 입력에 추가하려면 별도 특성 버전 변경이다.
- 소량 데이터로 상태 전이·누수·재현성 검사를 먼저 통과한 뒤 100호텔 전체를 생성한다. 호텔별/기간별 분할 저장과 인덱스로 과도한 메모리 적재·전체 이벤트 반복 스캔을 피한다. 성능을 측정하지 않은 처리 시간·메모리 한계를 보장하지 않는다.

8. 정확한 달력 분할, 라벨 성숙 경계 제거, 모든 포함/제외 사유 기록.
9. 평가 코드에 숨은 truth·시나리오·호텔 ID·미래 필드 유입 차단.
10. 학습 데이터·모델·API 입력의 이름·순서·자료형·버전 일치.

## 10. 기존 시스템과의 경계

Python 시뮬레이터는 오프라인 학습 자료를 생성한다. 실행 중인 Mock/ML/Agent는 Spring 업무 DB를 직접 수정하지 않는다. 공급사 CONFIRMED와 숙박일별 사실은 별개이며 위험 점수는 장애 확정 근거가 아니다. 현재 YB-001 Mock과 기존 Flyway·업무 DB는 이 문서 작성으로 바뀌지 않는다.

이 문서는 구현 코드·학습 완료 보고서가 아니다. 검수 항목은 앞으로 구현으로 증명해야 할 조건이며 현재 모두 통과했다고 주장하지 않는다.
