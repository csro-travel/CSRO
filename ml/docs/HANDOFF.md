## 4. 시뮬레이터의 원인→관측→정답

시뮬레이터는 공급사에 보이는 캐시 재고와 호텔 PMS의 실제 확보 상태를 분리합니다. 우리 플랫폼과 다른 채널이 같은 숙박일 재고를 두고 예약을 받으며, 플랫폼은 캐시상 가능하면 계약을 확정합니다. 전달 누락·지연, 다른 채널 확보, 늦은 캐시 갱신 때문에 계약 확정과 호텔 확보 결과가 달라질 수 있습니다.

전달 재시도·호텔 재확인·정해진 수동 복구 대기열을 거쳐 원호텔에서 복구되기도 합니다. 입실+2시간의 마감까지 실제 원계약을 이행하지 못하면 최종 거절이 발생합니다. 물리 객실 배정과 PMS 확보는 날짜별 용량을 넘지 않아야 하며, 단순히 같은 객실을 중복 배정하는 버그로 장애를 만들지 않습니다.

최종 이행·거절에서 원천 증빙 발행 작업이 발생합니다. 서비스 장애·증빙 발행 작업 유실·수집 재시도 때문에 플랫폼이 증빙을 관측하는 시점은 실제 결과 시점과 다를 수 있습니다. 이 관측 증빙만으로 지도학습 정답을 계산합니다.

- 전달이 누락됐어도 제때 복구되어 원호텔에서 전 기간 제공됐으면 정상 0이 될 수 있습니다.
- 원호텔 미제공 후 대체 호텔에서 해결돼도 원예약 장애 1은 유지합니다.
- 호텔 404·202·503, 공급사 취소 상태, 고객 주장·Agent 분석·위험 점수만으로 장애 1을 만들지 않습니다.
- 취소·노쇼·증빙 미수신·검증 미완료는 확인된 정상으로 바꾸지 않습니다.
- 최종 실패가 발생한 blocking night 외에 시도하지 않은 나머지 숙박일을 모두 실패로 채우지 않습니다.

`private_truth`는 원인과 물리 제약 검수용입니다. 원천 증빙을 관측하지 못한 행의 라벨을 숨은 truth로 보충하는 용도로 사용하지 않습니다. 증빙 발행 작업 유실은 기록되는 과정상의 장애이며 완성된 정답을 사후 독립 난수로 가리는 작업과 구분합니다.

## 5. 예측 대상 집합을 D-1에 고정

호텔 h, 체크인 D, 예측 시각 t에서 다음 조건을 만족하는 우리 플랫폼 예약을 모아 집합 C를 고정합니다.

1. 해당 호텔·체크인 날짜의 예약
2. t까지 이용 가능한 상태 이벤트로 재구성한 공급사 계약이 `CONFIRMED`
3. t까지 취소가 관측되지 않음

`occurred_at <= t`와 `available_at <= t`를 모두 적용합니다. t 이후 신규 예약은 실제 재고 경쟁에 참여할 수 있지만 이미 고정한 C에는 추가하지 않습니다. 늦게 받은 과거 취소도 이전 C를 소급 변경하지 않습니다.

예약별 관측 정답을 호텔·날짜로 OR 집계합니다.

| 호텔·날짜 정답 | 조건 |
| --- | --- |
| `1` | C 중 확인된 원예약 장애 1이 최소 한 건 존재 |
| `0` | C가 비지 않고 모든 예약이 확인된 정상 0 |
| `UNKNOWN` | 위 조건에 해당하지 않음 |
| `NOT_ELIGIBLE` | C가 비어 있음 |

다른 예약이 미확인이어도 이미 확인된 장애 한 건이 있으면 1입니다. 반대로 미확인 예약이 하나라도 남아 있으면 전체 정상 0으로 채우지 않습니다. 1의 `label_available_at`은 첫 유효 장애 증빙이 이용 가능해진 시각, 0은 모든 정상 결과의 확인 시각 중 최댓값입니다.

## 6. 입력 계약 — risk-features-0.2

| 순서 | 필드 | 자료형·핵심 산식 |
| --- | --- | --- |
| 1 | `pastFailureRate90d` | 숫자. 과거 90일의 확인 완료 예약 장애율 `(f+1)/(n+20)` |
| 2 | `targetConfirmedBookingCount` | 0 이상 정수. D-1 고정 집합 C의 예약 건수 |
| 3 | `bookingVolumeGrowth7d` | 숫자. `(최근7일+1)/(직전28일/4+1)-1`, [-1,10] clipping |
| 4 | `reconfirmationOverdueRate7d` | 0~1. 최근 7일 최초 확인 기한 도래 중 유효 회신 기한 초과 비율 |
| 5 | `inventoryUnavailableRate7d` | 0~1. 같은 표준 조건의 유효 판매 조회에서 캐시상 판매 가능 수량이 1개 미만인 비율 |
| 6 | `isPeakDay` | boolean. 금·토 체크인, 7~8월 또는 사전 고정 가상 성수일 |

과거율은 예약별 결과를 사용하며 호텔·날짜 OR 라벨의 비율과 섞지 않습니다. UNKNOWN·취소·노쇼·미완료는 과거율 분모에서 제외합니다. `label_available_at <= asOf`인 과거 정답만 사용합니다. 이력이 없으면 Beta(1,19)의 0.05를 사용하되 현실 장애율로 해석하지 않습니다.

재확인 유효 회신은 예약·호텔·숙박일이 맞는 200 날짜별 회신입니다. `UNAVAILABLE` 주장도 회신 형식이 맞으면 유효할 수 있으며, 202·404·503·타임아웃은 완료 회신이 아닙니다. 늦은 회신으로 당시 기한 초과 기록을 지우지 않습니다.

판매 조회는 `STANDARD`, D 체크인/D+1 체크아웃, 성인2·객실1·KRW 조건으로 통일합니다. 공급사에 보인 캐시 신호를 사용하며 실제 비공개 PMS 잔여 재고를 직접 읽지 않습니다. 유효 수량 응답이 없는 오류는 분모에서 제외합니다. 판매 조회의 부족 신호는 원예약 미제공의 확정 근거가 아닙니다.

각 특성의 분모·무관측 원인·raw 값·clipping 여부는 감사 열로 보존하지만 모델 입력에 추가하지 않습니다. 입력은 스키마에 명시한 위 여섯 개만 선택합니다. 호텔 ID, 예약 ID, 미래 사건, 숨은 성향, 장애 원인, truth, 정답, 정답 시각은 제외합니다.

현재 API-023의 임시 `risk-features-0.1`과 이름·순서·자료형이 같은 것으로 가정하지 않습니다. `examples/risk-request.json`은 새 계약의 CLI 요청 예제이며 HTTP endpoint 구현 완료를 뜻하지 않습니다.

## 7. 학습·모델 선택·최종 평가

2025년 4~9월 학습, 10월 검증, 11~12월 테스트를 고정합니다. 학습 라벨은 9월 30일 09시 이전, 검증 라벨은 10월 31일 09시 이전에 관측되어 있어야 하며 경계 이상 시각은 제거합니다. 테스트 라벨은 고정 추출 시각까지 관측된 값만 사용합니다. UNKNOWN·NOT_ELIGIBLE과 제외 사유를 `split_audit.csv`에 보존합니다.

비교 대상은 다음과 같습니다.

- 주 규칙: `1-(1-pastFailureRate90d)^targetConfirmedBookingCount`
- 참고 규칙: `pastFailureRate90d`
- LightGBM: 동일한 여섯 특성, seed 42, 단일 스레드·deterministic 설정

주 규칙은 예약 독립 가정으로 노출량을 반영한 비교 점수입니다. 실제로 보정된 장애 확률이라고 주장하지 않습니다.

LightGBM 후보는 `num_leaves={7,15,31}` × `min_child_samples={30,100}`으로 제한합니다. 검증 AP를 우선하고 동률이면 단순한 모델을 택합니다. 각 모델의 분류 임계값은 검증 F1을 최대화하되 동률이면 precision, 이후 높은 임계값을 택합니다. 모델·임계값을 고정한 다음 테스트를 봅니다.

최종 모델은 4~9월 학습 checkpoint입니다. 이번 버전에서는 학습+검증 재학습을 하지 않습니다. 생성 규칙·특성·탐색 범위가 바뀌면 데이터/모델 버전과 평가를 구분합니다.

보고할 항목은 AP, ROC-AUC, precision/recall/F1, 혼동행렬, 표본 수·양성률·라벨 관측률입니다. 한 클래스만 남아 정의되지 않는 지표는 null과 사유를 남깁니다. AP 방식은 곡선 적분 방식의 다른 PR-AUC와 무조건 같은 값으로 취급하지 않습니다.

일일 상위 K=10은 가상 검토 예산입니다. 전체 적격 대기열에서 점수 내림차순·동점 호텔 ID순으로 선택하고 UNKNOWN이 차지한 자리를 유지합니다. 확인된 표본만의 성능에 더해 전체 선택 수, UNKNOWN 수, precision 하한·상한, 확인 양성에 대한 recall을 함께 봅니다.

과거 장애율의 기여는 검증 permutation importance와 해당 특성을 제거한 비교로 점검합니다. 중요도 1위가 아니면 그대로 보고하며 순위를 강제하기 위해 정답이나 테스트 조건을 바꾸지 않습니다.

## 8. 재현성과 산출물 인계

전체 생성은 실행 전 `effective_config.json`에 `config_frozen_for_final_test=true`를 고정하고, 설정 해시·`experiment_lock.json`을 남깁니다. 원본 설정의 false는 검수 전 템플릿 상태이며 사용자가 수동으로 바꿀 필요는 없습니다. 파일럿은 false로 유지합니다. 테스트 결과를 본 뒤 같은 고정 기록 아래 규칙을 몰래 수정하지 않습니다.

| 모델 출력의 `model.txt`, `model_metadata.json` | LightGBM checkpoint·버전·특성 계약·학습 설정 |
| `evaluation_report.json`, `evaluation_report.md`, `search_results.csv`, `test_predictions.csv` | 평가 요약·후보 비교·개별 평가 점수 |
| `audit_slices.json` | 모델 선택 후 결합한 호텔 규모·프로필·원인·관측률 진단. 정답 보충이나 모델 입력으로 사용하지 않음 |
| `runtime_environment.json` | 실제 생성 환경과 라이브러리 버전 |

관측 증빙을 별도 숨은 truth에서 채워 넣지 않습니다. Parquet의 중첩 값은 JSON 문자열로 저장될 수 있으므로 원천·감사 도구에서 스키마를 확인하고 읽습니다. CSV에 감사 열이 함께 있더라도 모델 입력은 명시한 여섯 특성으로 제한합니다.

동일 seed 외에도 코드·설정·의존성 버전·특성 순서·파일 해시가 맞아야 합니다. RNG는 목적별 안정적인 component ID로 분리하며 Python 프로세스의 임의 `hash()`를 seed로 사용하지 않습니다. 실행 시간처럼 매번 달라지는 운영 정보와 재현 대상 데이터를 구분합니다.

Windows 사용자는 README의 `py -3.13`과 `.venv\Scripts\python.exe` 명령을 사용합니다. 클라우드에서의 테스트·학습 기록과 사용자의 Windows 실행 확인은 별도로 기록합니다. 파일럿 정합성 통과, 전체 데이터 생성, 모델 학습, 최종 성능 확인은 각각 다른 완료 단계입니다.

이번 실험은 고정 복구 정책 아래의 가상 결과를 예측합니다. 모델이 복구 순서나 라벨을 바꾸지 않으므로 AI 개입의 인과적 개선 효과를 측정하지 않습니다. 같은 호텔이 학습과 이후 평가 기간에 반복되며 처음 보는 호텔의 일반화 성능도 아닙니다. 관측하기 어려운 호텔이 확인 라벨 평가에서 빠지는 선택 편향을 보고합니다.
