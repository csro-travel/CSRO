# API-023 — 호텔·체크인 날짜 위험 점수 추론

Spring이 전달한 **`risk-features-0.2` 여섯 특성**을 저장된 LightGBM 기준 모델로 추론하는 내부 HTTP API다. 요청 시점에 데이터를 생성하거나 모델을 다시 학습하지 않으며, Python은 업무 DB를 읽거나 수정하지 않는다.

| 항목 | 계약 |
| --- | --- |
| Method / URI | `POST /internal/v1/risk-assessments` |
| 호출 방향 | A팀 Spring → A팀 Python ML |
| 로컬 제안 주소 | `http://127.0.0.1:8002` |
| 인증 | `Authorization: Bearer {ML_SERVICE_TOKEN}` |
| 요청 / 정상 응답 | `application/json` |
| 오류 응답 | `application/problem+json` |
| 입력 버전 | `risk-features-0.2`만 지원 |
| 기본 사용 모델 | `process-synthetic-lightgbm-0.2-84d386281d22` |

8002는 이번 로컬 실행에서 사용할 제안 포트다. 공통 배포 주소나 다른 팀의 실행 포트 변경을 확정한 것은 아니다. Windows 설치·호출 절차는 [API-023_HANDOFF.md](API-023_HANDOFF.md)를 따른다.

## 1. 원 설계와 v0.2의 관계

[Notion API-023 계약 검토안](https://app.notion.com/p/417e04d22bed8136935fc2504f94525f)의 URI, 호출 방향, 성공 응답 6개 필드, 서비스 인증, 오류 상태, Spring/Python 책임을 유지한다.

원문에 있는 `risk-features-0.1`의 여섯 필드와 점수 0.78은 가상 예시다. 이번 구현은 이미 학습한 모델의 **명시적인 v0.2 특성 계약**을 HTTP로 제공한다. v0.1 필드를 조용히 변환하거나 같은 의미로 간주하지 않는다. v0.1 요청은 422로 거부한다.

과거 장애율을 주요 신호로 삼는다는 점은 팀 합의이며, 여섯 특성의 구체적 선택·산식과 시뮬레이터 매개변수는 담당 설계안이다. 이번 HTTP 구현이 전체 특성 계약의 팀 승인 완료를 뜻하지 않는다. 계산 기준은 [ML_DATA_RULES_v0.2.md](../ML_DATA_RULES_v0.2.md), 입력 스키마는 [features-v0.2.schema.json](../../schemas/features-v0.2.schema.json)을 따른다.

## 2. 요청

`Authorization`과 `Content-Type`은 필수이며, `Accept: application/json`은 권장이다. 구현은 `Accept` 헤더의 존재를 필수로 검사하지 않는다.

```http
Authorization: Bearer {ML_SERVICE_TOKEN}
Content-Type: application/json
Accept: application/json
```

Path·Query 파라미터는 없다. 요청 예제는 기존 [risk-request.json](../../examples/risk-request.json)과 같다.

```json
{
  "hotelId": "HOTEL-001",
  "targetCheckInDate": "2025-11-01",
  "asOf": "2025-10-31T09:00:00+09:00",
  "featureSetVersion": "risk-features-0.2",
  "features": {
    "pastFailureRate90d": 0.05,
    "targetConfirmedBookingCount": 12,
    "bookingVolumeGrowth7d": 0.4,
    "reconfirmationOverdueRate7d": 0.2,
    "inventoryUnavailableRate7d": 0.1,
    "isPeakDay": false
  }
}
```

| 필드 | 타입·검증 |
| --- | --- |
| `hotelId` | 비어 있지 않은 문자열. 내부 DB PK나 예약번호가 아닌 호텔 식별자 |
| `targetCheckInDate` | `YYYY-MM-DD` 체크인 날짜 |
| `asOf` | 시간대가 포함된 ISO 시각. 해당 체크인 날짜 D-1의 09:00 Asia/Seoul과 일치 |
| `featureSetVersion` | 문자열 `risk-features-0.2` |
| `features` | 아래 6개 필드만 포함하는 객체 |

| 특성 | 타입·범위 | 의미 |
| --- | --- | --- |
| `pastFailureRate90d` | 숫자, 0~1 | 관측 완료 과거 예약 장애율의 Beta(1,19) 보정값 |
| `targetConfirmedBookingCount` | 정수, 0 이상 | D-1에 고정한 대상 확정 예약 건수 |
| `bookingVolumeGrowth7d` | 숫자, -1~10 | 최근 확정 유입 증가율 |
| `reconfirmationOverdueRate7d` | 숫자, 0~1 | 최근 최초 확인 기한 초과 비율 |
| `inventoryUnavailableRate7d` | 숫자, 0~1 | 동일 표준 조건의 유효 판매 조회 중 판매 수량 부족 비율 |
| `isPeakDay` | boolean | 사전 고정 성수일 여부 |

JSON Schema의 정수 의미를 적용하므로 예약 건수 `12.0`처럼 소수 부분이 없는 숫자도 정수값으로 허용한다. 문자열 숫자·boolean을 숫자 대신 전달하는 타입 변환은 하지 않는다. 유한한 값만 허용하며 NaN·Infinity는 정상 입력이 아니다. 호텔 ID·정답·감사 열을 `features`에 추가하지 않는다.

API는 값의 형식·범위·D-1 시각을 검사한다. 해당 값이 실제로 `asOf` 당시 관측됐는지, 올바른 분모와 대상 집합으로 집계됐는지는 Spring의 특성 생성 파이프라인에서 보장해야 한다. Python이 요청 호텔을 업무 DB에서 찾아 값을 보충하거나 호텔의 존재를 확인하는 API가 아니다.

`asOf`는 같은 시점을 나타내는 UTC 표현(예제에서는 `2025-10-31T00:00:00Z`)도 허용하며 응답에는 요청 문자열을 그대로 돌려준다.

## 3. 정상 응답 — 200

성공 JSON은 다음 6개 필드를 직접 반환한다. 별도 `data` 봉투나 고객용 DTO로 감싸지 않는다. 기준 요청·모델의 예상 응답은 다음과 같다.

```json
{
  "hotelId": "HOTEL-001",
  "targetCheckInDate": "2025-11-01",
  "asOf": "2025-10-31T09:00:00+09:00",
  "riskScore": 0.38033996022231914,
  "modelVersion": "process-synthetic-lightgbm-0.2-84d386281d22",
  "featureSetVersion": "risk-features-0.2"
}
```

`hotelId`, `targetCheckInDate`, `asOf`는 요청 대상·시점을 반영한다. `riskScore`는 0~1의 위험 선별 점수이며, 보정된 실제 장애 확률이나 객실 미제공 확정 근거가 아니다. 낮은 점수도 200 정상 결과다.

2025년 입력은 모델·HTTP 계약을 확인하는 합성 예제다. 이 요청으로 2026년 YB-001의 현재 업무 DB나 실제 호텔 상태를 관측한 것은 아니다. XGBoost 후속 비교 권고가 있어도 이 API의 기준 모델을 자동 교체하지 않는다.

## 4. 오류 계약

추론 endpoint의 오류는 평평한 Problem JSON을 반환한다. `detail`에 FastAPI 내부 validation 배열이나 예외 스택을 그대로 노출하지 않는다.

```json
{
  "type": "about:blank",
  "title": "Unprocessable Content",
  "status": 422,
  "detail": "The feature schema version is unsupported.",
  "code": "FEATURE_SCHEMA_UNSUPPORTED",
  "traceId": "11111111-1111-4111-8111-111111111111"
}
```

| HTTP | 안정적인 `code` | 의미 |
| --- | --- | --- |
| 400 | `INVALID_RISK_REQUEST` | JSON·Content-Type 오류, 최상위 5개 필드 누락·추가, 필드 타입·날짜/시각 형식 오류 |
| 401 | `UNAUTHENTICATED_SERVICE` | 서비스 토큰 누락·불일치 또는 서버 토큰 미설정 |
| 422 | `FEATURE_SCHEMA_UNSUPPORTED` | 지원하지 않는 특성 버전 |
| 422 | `INVALID_FEATURE_VALUES` | 특성 누락·추가·범위 오류 또는 D-1 시각 불일치 |
| 503 | `MODEL_UNAVAILABLE` | 모델이 없거나 무결성·메타데이터·로딩 검사에 실패해 추론 불가 |
| 500 | `INTERNAL_ERROR` | 예기치 못한 내부 추론 오류 |

검사 순서는 인증 → 요청 계약 → 모델 준비 상태다. 예를 들어 토큰이 없으면 잘못된 본문이나 모델 상태를 공개하기 전에 401을 반환한다. 응답의 `X-Request-ID`와 오류 본문의 `traceId`는 같은 추적 ID이며 응답은 `Cache-Control: no-store`를 사용한다.

401·422·503을 위험 점수 0이나 정상 예약으로 치환하지 않는다. Spring은 오류와 추론 실패를 기록하고 재시도·수동 대응 정책을 별도로 적용한다.

## 5. 기동·모델·준비 상태

`travel_ml.risk_api:app`이 HTTP 앱이며, `risk_runtime.py`가 기준 모델의 로딩·입력 검증·추론을 맡는다. 모델은 프로세스 기동 시 한 번 검증·로드하며, 검증한 동일 모델 바이트를 메모리에서 재사용한다. 요청마다 재학습하거나 모델을 다시 불러오는 API가 아니다.

- `ML_SERVICE_TOKEN`: 필수 서비스 토큰. 기본 토큰으로 우회하지 않는다. 비어 있으면 추론을 허용하지 않는다.
- `ML_MODEL_DIR`: 선택 사항. 기본값은 `ml/artifacts/reference_model_v02`다. 상대 경로는 `ml` 루트 기준으로 해석한다.
- 토큰과 모델 경로는 앱 생성 시 읽으므로 서버 실행 전에 설정하고, 변경 후에는 재시작한다. `.env`를 자동으로 읽는 서버는 아니다.
- 모델 폴더 전체 8개 파일의 집합·해시·메타데이터·특성 순서·실제 모델 checkpoint를 함께 검증한다. manifest·메타데이터·특성 계약·실제 모델 파일을 함께 유지한다. 일부 파일만 복사하거나 모델 폴더 안에 로그·설명 파일을 추가하지 않는다.

| Endpoint | 인증 | 동작 |
| --- | --- | --- |
| `GET /healthz` | 없음 | 프로세스 생존 확인, 200 `{"status":"alive","modelReady":true}`. `modelReady`는 상태에 따라 false |
| `GET /readyz` | 없음 | 모델·인증 설정이 준비됐으면 200 `{"status":"ready","modelReady":true,"authConfigured":true}` |
| `GET /readyz` | 없음 | 준비되지 않았으면 503, `status=not_ready`와 두 준비 상태 boolean |

`/readyz`의 503은 위 표의 진단 JSON이며 추론 endpoint의 Problem 응답과 구분한다.

토큰이 없거나 모델이 준비되지 않아도 프로세스는 기동할 수 있다. `/healthz`의 200만으로 추론 준비 완료를 판단하지 않는다. 토큰 미설정 시 `/readyz`는 503이고 추론은 401이다.

모델 로딩에 실패한 프로세스가 요청마다 자동 재시도하는 구조는 아니다. 파일을 복구했다면 서버를 재시작해 기동 검사를 다시 수행한다. 모델을 교체할 때는 기존 폴더를 실행 중에 덮어쓰는 절차 대신 새 모델 묶음의 계약·검증과 서버 재시작을 함께 관리한다. 운영 모델 교체·배포 자동화는 이번 범위가 아니다.

## 6. Spring과 ML의 책임

| Spring | Python ML |
| --- | --- |
| `asOf` 당시 이용 가능한 원천 이벤트로 여섯 특성·고정 대상 집합 집계 | 지원 버전·타입·범위·D-1 시각 검사 |
| 내부 서비스 인증 헤더와 요청·응답 대상 검증 | 서비스 토큰 검증·저장 모델 추론·점수/버전 반환 |
| RiskAssessment와 실패 기록 저장 | 업무 DB를 읽거나 수정하지 않음 |
| 운영 임계값·재확인 처리량·대상 예약 선별 | 위험 점수만 반환, 업무 임계값·Case 생성 결정 안 함 |
| 공급사·호텔 재확인, 원문 검증·숙박일 사실 채택 | 공급사 CONFIRMED나 개별 숙박일 상태를 추론 응답에 섞지 않음 |

Python HTTP 단독 호출 성공과 실제 Spring 연동 E2E는 구분한다. 원 설계의 업무 흐름 전체나 실제 데이터 성능을 이번 API 구현 완료로 보고하지 않는다.
