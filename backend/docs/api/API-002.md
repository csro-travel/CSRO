# API-002 고객 체크인 문제 신고

기준은 [Notion API-002 상세 검토안](https://app.notion.com/p/8952f2597c5783a0a3f2813647f2dc9e)과 [업무 E2E](https://app.notion.com/p/cfb2f2597c57821bb16e014bdc22c147)이다. 사용자의 구현 요청에 따라 기존 URI·JSON·상태 코드와 현재 V1 물리 구조에 매핑했다. Notion의 팀 전체 설계 승인 상태를 변경한 것은 아니다.

## 접수 계약

`POST /api/v1/bookings/{bookingId}/incident-reports`는 인증된 활성 고객 본인의 예약만 접수한다. 미존재·타인 예약은 같은 `404 BOOKING_NOT_FOUND`다. 고객 ID·사건 ID·긴급도·호텔 사실·ML 점수·접수 시각을 본문에서 받지 않는다.

필수 헤더는 `Content-Type: application/json`, `Authorization: Bearer …`, `Idempotency-Key`다. 키는 영숫자와 `._:-`를 사용하는 1~100자다. 일반 로그인·토큰 발급은 기존과 같이 후속이며, 서블릿 Principal을 활성 사용자와 대조한다. 아래 격리 시연에서만 별도 고객 토큰을 고정 가상 고객에 연결한다.

```json
{"issueType":"CHECKIN_FAILED","atHotel":true,"message":"호텔에서 예약을 찾지 못한다고 합니다."}
```

위 세 필드만 허용한다. `atHotel`은 실제 boolean이며 false도 접수한다. 현장 여부는 고객의 자기 신고다. `message`는 앞뒤 공백을 제거한 1~1000자이며 원문은 HTML로 실행하지 않는다.

성공은 새 사건과 기존 사건 연결 모두 `201`, `Cache-Control: private, no-store`다.

```json
{
  "reportId":"IR-001",
  "bookingId":"YB-001",
  "chatMessageId":"MSG-001",
  "case":{"caseId":"C-001","created":true,"status":"OPEN","priority":"URGENT"},
  "verificationStatus":"PENDING",
  "receivedAt":"2026-11-25T09:00:00Z"
}
```

같은 예약·키·정규화 본문은 최초 응답 스냅샷을 재생한다. 이후 사건의 상태가 바뀌거나 종료돼도 옛 요청으로 사건을 다시 열지 않는다. 같은 키의 다른 본문은 `409 IDEMPOTENCY_KEY_REUSED`다. 응답 유실 시 같은 본문·같은 키로 재시도하고, 실제 새로운 신고에만 새 키를 사용한다.

오류는 `application/problem+json`의 `type/title/status/detail/code/traceId`다. 잘못된 본문·키는 `400 INVALID_INCIDENT_REPORT`, 미인증·비활성 계정은 `401 UNAUTHENTICATED`, 고객 외 역할은 `403 FORBIDDEN_ROLE`, 미존재·타인 예약은 `404 BOOKING_NOT_FOUND`다. 지원하지 않는 Content-Type은 `415 UNSUPPORTED_MEDIA_TYPE`, 예상치 못한 오류는 `500 INTERNAL_ERROR`이며 내부 SQL·고객 원문·토큰을 응답하지 않는다.

## 저장과 재확인 책임

- 같은 예약 행을 먼저 잠근 뒤 활성 사건을 생성·재사용한다. 새 사건은 OPEN/URGENT와 필수 CONTACT_CUSTOMER TODO를 가진다. 기존 WAITING/IN_PROGRESS 상태·담당자는 유지하고 긴급도와 확인 업무를 갱신한다.
- 신고·첫 고객 TEXT 메시지·사건/업무·감사·재확인 대기 기록은 한 트랜잭션이다. 실패하면 함께 롤백한다. 새 키의 추가 신고는 이력을 추가하며 활성 사건은 한 건이다.
- 고객 신고를 호텔 근거로 저장하거나 supplier_status·booking_nights를 변경하지 않는다. `verificationStatus=PENDING`은 접수 스냅샷이며 이후 검증 상태의 조회 API가 아니다.
- 물리 `jobs`의 기존 RECHECK를 사용한다. 활성 작업이 있으면 중복 생성 대신 그 번호를 감사 기록에 연결한다. 기존 위험 작업의 평가·프로토콜·요청번호를 덮어쓰지 않는다.
- 고객 신고 전용 작업은 `incident-recheck-v1`로 구분한다. 커밋 후 작업자가 기존 API-026/027 호출·검증 경로를 사용한다. HTTP는 행 잠금 밖에서 실행하고, 검증된 근거 반영과 작업 완료는 같은 트랜잭션으로 처리한다.
- 미확인·202·외부 장애는 객실 불가 확정이 아니다. 제한된 재시도는 같은 요청번호를 유지하며, 기한/예산 소진 뒤에도 사건과 필수 확인 업무는 남는다. 기존 위험 프로토콜은 그 소유 서비스에 위임하고, 알 수 없는 프로토콜을 탈취하지 않는다.

기존 Flyway V1·DB 제약·ML 모델·Agent 계약은 변경하지 않는다. Spring→API-024 자연어 분석 호출·분석 저장, 운영 로그인, 상시 운영 스케줄러, 실제 공급사·결제·환불 연동은 이번 구현에 포함하지 않는다.

## 격리 시연

기존 [제안·선택 시연](OFFERS-DEMO.md) 또는 [대체 예약 시연](REPLACEMENT-DEMO.md)의 전용 `local-chat-demo` DB·서버 토큰·고객 토큰을 유지한다. DB는 `127.0.0.1:25434/yeohaengbom_chat_demo`, 사용자 `yb_chat_demo`이며 일반 업무 DB에 시연 설정을 적용하지 않는다. 새로운 DB를 만들 필요 없이 이미 실행 중인 전용 DB를 사용할 수 있다.

1. `backend`에서 `./gradlew.bat bootJar`로 빌드한다. 기존 Spring 프로세스를 정상 종료하고, 같은 환경에서 `--spring.profiles.active=local-chat-demo --incident.recheck.worker.enabled=true`를 기존 JAR 실행 옵션에 추가한다. 기본은 꺼짐이며 다른 프로필에서는 켤 수 없다. 기존 quote/replacement 옵션은 필요한 시연 범위에 맞춰 유지한다.
2. API-026/027 Mock 서버와 Spring의 `booking.reconfirmation.mock.base-url/service-token`을 연결한다. 신고 접수 자체는 Mock이 꺼져 있어도 저장된다. Mock 연결 실패는 이미 반환한 201을 취소하지 않는다.
3. 고객 3101 프록시를 시작하기 전에 `CSRO_CUSTOMER_DEMO_PROXY=true`, `CSRO_INCIDENT_DEMO_PROXY=true`, `CSRO_CUSTOMER_DEMO_TOKEN`을 설정한다. 기존 `CSRO_LOCAL_DEMO=true`, `PORT=3101`, `CSRO_DEMO_SPRING_PORT=18082`를 유지한다. 상담사 3100 프록시에 고객 신고 쓰기를 개방하지 않는다.
4. 빌드한 고객 화면 `http://127.0.0.1:3101/customer/bookings/YB-001`에서 신고한다. 접수된 사건 번호로 고객 상담 화면에 이동하며 상담사 목록에서도 같은 사건을 확인한다. 이미 사건이 있으면 그 사건을 재사용한다. 번호 C-001을 고정 결과로 가정하지 않는다.

클라이언트는 미확정 요청의 본문·키를 탭의 sessionStorage에 보관한다. 응답 유실 중에는 내용을 바꾸어 새 신고를 만들지 않고 같은 요청을 재시도한다. 성공·명시적 거절 뒤에만 새 신고를 준비한다. 브라우저에는 서버 토큰을 전달하지 않는다. 여러 기기 간 미확정 요청 복구나 운영용 고객 앱을 구현한 것은 아니다.

## 검증

`backend`에서 단위 검사와 전용 PostgreSQL 검사를 구분한다.

```powershell
.\gradlew.bat test --tests 'com.csro.backend.incidents.*' --tests '*LocalChatDemoAuthenticationTest'
```

쓰기 검사를 실행하려면 먼저 별도의 테스트 PostgreSQL을 준비하고 다음을 프로세스 환경으로 전달한다. 비밀번호는 Git에 기록하지 않는다.

```powershell
$env:INCIDENT_REPORT_TEST = 'true'
$env:INCIDENT_REPORT_TEST_DB_URL = 'jdbc:postgresql://127.0.0.1:25446/yeohaengbom_incidents_test'
$env:INCIDENT_REPORT_TEST_DB_USER = 'yb_incident_test'
# INCIDENT_REPORT_TEST_DB_PASSWORD에는 별도 테스트 DB 비밀번호를 설정한다.
.\gradlew.bat test --tests 'com.csro.backend.incidents.*IntegrationTest'
```

테스트는 설정과 실제 DB·사용자 신원을 Flyway 전에 대조한다. 이름이 다른 기존 업무/시연 DB로 우회하지 않는다. 프런트 검사는 `pnpm build`, `pnpm exec tsc --noEmit`, `node --test tests/demo-incidents-proxy.cjs`다. 실제 실행 결과와 미검증 범위는 PR에 요약한다.

Linux에서 API-002·시연 인증 단위 17개와 전용 PostgreSQL 검사 15개가 통과했다. 같은 키/다른 키의 동시 접수, 전체 롤백, WAITING 유지, 종료 후 최초 응답 재생, 외부 작업 보존, 503→202→검증 성공, 재시작, 실행권 상실 시 근거 롤백과 재시도 한도를 검사했다. 단위 검사와 DB 검사는 구분해 실행했으며 최종 관련 변경 뒤 해당 DB 검사를 다시 확인했다.

프런트 빌드·별도 TypeScript·기존 기능을 포함한 프록시 20개가 통과했다. `tests/customer-incidents-browser.py`는 합성 HTTP 응답을 제어하여 false 현장 여부, 응답 유실 뒤 새로고침·동일 키/본문 재시도, 저장소 실패 시 전송 차단을 검사한다.

별도로 실제 모바일 크기 브라우저→고객 프록시→Spring→격리 시연 DB→고객 채팅·상담사 사건을 연결했다. 서로 다른 신고 2건과 재전송 후 사건/작업은 각각 1건, 재확인 전 근거 0건·3박 모두 UNKNOWN/UNCONFIRMED였다. Spring을 재시작해 작업자를 켠 뒤 기존 작업은 COMPLETED, 근거는 2건이었고 첫날만 VERIFIED/UNAVAILABLE로 바뀌었다. 나머지 숙박일·공급사 CONFIRMED·OPEN 사건을 유지하고 ML 평가 없이 접수·재확인했다. 검증 이후에도 최초 201 스냅샷은 같았다.

이 결과는 합성 시연의 접수·정합성 검증이다. Windows의 이번 API-002 재현, 원격 GitHub Actions 완료, 운영 인증·실제 호텔 성능·API-024 자연어 연결·입실/종료 완료를 증명하지 않는다.
