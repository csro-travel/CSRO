# 사건 긴급도 구분 — 사전 발견은 일반, 고객 신고는 긴급

**상태: 구현함(2026-11-28, 브랜치 `1129cy-followups`).** 사용자가 2026-11-28 대화에서 "긴급·일반 구분"을 지시했다. 구분 기준은 아래 한 가지이며 팀 확인 전이다.

## 왜 필요한가

두 생성 경로가 모두 사건을 `URGENT`로 만들어 상담 대응 목록의 모든 건이 긴급이었다. 긴급 표시·정렬·긴급 알림이 구분 역할을 하지 못했다.

## 규칙

| 사건이 생긴 경로 | 긴급도 | 근거 |
| --- | --- | --- |
| 위험 점검 재확인에서 제공 불가가 확인됨 | `NORMAL` | 고객이 아직 모르는 상태에서 미리 찾은 건이다 |
| 고객이 체크인 문제를 신고함 | `URGENT` | 고객이 기다리고 있다. 기존 동작 그대로다 |
| 일반 사건에 고객 신고가 들어옴 | `URGENT`로 올림 | 기존 동작 그대로다(`IncidentReportService`) |

한 문장으로는 "고객이 지금 기다리고 있는가"다. 체크인까지 남은 시간은 기준에 넣지 않았다. 시연 데이터는 판단 시각이 체크인 전날로 고정돼 있어 시간 기준으로는 다시 전부 긴급이 된다.

## 바뀐 곳

- `reconfirmation/BookingReconfirmationEvidenceService.createCase`: `'URGENT'` → `'NORMAL'` 한 곳.
- 값의 종류(`URGENT`·`NORMAL`), 응답 필드, 목록 정렬(긴급 먼저), DB 제약은 그대로다. Flyway 변경 없음.
- 검사 기대값: `BookingReconfirmationEvidenceIntegrationTest`, `RiskCaseDemoLiveTest`.

## 영향

- 시연 2의 C-001이 일반으로 생성된다. 목록에서 고객 신고 건 아래에 놓이고 긴급 알림에 뜨지 않는다.
- 홈의 "먼저 처리할 대응 건"은 긴급이거나 다음 업무가 있는 건을 보여 주므로 일반 건도 다음 업무가 있으면 나온다.
- 이미 만들어진 사건의 긴급도는 바꾸지 않는다.

## 대안

체크인 임박(예: 24시간 이내)이나 제공 불가 숙박일 수를 기준에 더할 수 있다. 판단 시각을 다루는 규칙이 필요해 이번에는 넣지 않았다.
