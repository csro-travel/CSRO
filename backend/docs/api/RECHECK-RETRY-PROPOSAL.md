# 상담사의 호텔 재확인 다시 요청 — 제안(구현하지 않음)

**상태: 승인 대기. 구현하지 않았다.** 사용자가 2026-11-28 대화에서 진행을 지시했지만, 아래 이유로 코드를 쓰기 전에 범위 확인이 필요하다.

## 하려는 것

미확인 숙박일이 남은 사건에서 상담사가 "호텔에 다시 확인 요청"을 눌러 자동 재확인을 한 번 더 실행한다. 지금은 자동 재확인이 끝나면(고객 신고 경로는 30초 간격 3회) 상담사의 통화 기록(API-006)만 미확인을 풀 수 있다.

## 왜 바로 구현하지 않았나

1. **재확인 작업이 접수 건에 묶여 있다.** `incidents/IncidentRecheckJobs`의 작업은 고객 신고 번호가 필수이고(`reportId < 1`이면 거절), 작업 번호가 `INC-{신고}-{예약}`으로 고정이며 소유 검증(`validateOwned`)이 이 형식을 다시 확인한다. 같은 신고로 두 번째 작업을 만들 수 없다.
2. **사전 점검으로 생긴 사건에는 신고가 없다.** 이 경로의 재확인은 `risk/RiskRecheckJobs`가 위험 평가에 묶어 만든다. 상담사 요청을 받으려면 두 작업 체계 중 하나에 "상담사 요청" 경로를 새로 내야 한다.
3. **재확인 상태 기계는 A팀(ML) 영역이고 CI의 실행 검사(`incidents`, `risk` 작업)가 붙어 있다.** 제출 직전에 건드리기에는 범위가 크다.
4. **시연에서는 결과가 달라지지 않는다.** Mock 호텔 회신은 예약마다 고정이다(`mock-server/app/fixtures.py`: "No randomness"). 다시 요청해도 같은 "확인 중" 또는 응답 대기가 돌아온다.

## 구현한다면

- `POST /api/v1/cases/{caseId}/rechecks`(상담사 전용, `Idempotency-Key` 필수). 진행 중인 재확인이 있으면 그 작업을 돌려주고 새로 만들지 않는다.
- 작업 종류는 기존 `RECHECK`, `trigger_type`에 `COUNSELOR_REQUEST`를 추가한다. `jobs.trigger_type`에는 CHECK 제약이 없어 Flyway 변경은 필요 없다.
- 작업 매개변수의 신고 번호를 선택 값으로 바꾸고 작업 번호 형식에 순번을 더한다(예: `CNS-{사건}-{순번}`). 소유 검증과 완료 처리(근거 저장, 실패 시 `VERIFY_HOTEL` 업무)가 이 형식을 받도록 고친다.
- 한 사건에서 다시 요청할 수 있는 횟수와 간격을 정해야 한다(업무 규칙).
- 화면: "호텔 측 회신"의 통화 결과 입력 옆에 버튼, 진행 상태는 기존 처리 이력에 표시.

## 결정이 필요한 것

- A팀과 작업 형식 변경을 합의할지, 이 기능을 제출 범위에서 뺄지.
- 재요청 횟수·간격 한도.
