# 대체 숙소 개별 전송(1~3곳 제안) — API-013 최소 변경 제안

**상태: 사용자가 2026-11-27 대화에서 "11-28 기능 마감 뒤 별도 PR로 구현"을 결정. 아직 구현하지 않았다.** "항상 3곳" 업무 규칙이 풀리는 점은 팀 확인 전이다. 구현 PR 전에는 코드·테스트·시연 문서를 바꾸지 않는다.

기준은 `1127cy-overnight`의 `c46e73a`다. [API-013/014 최소 계약](API-013-014-PROPOSAL.md)의 "정확히 3개" 조건을 바꾸는 제안이며, Notion 원본은 수정하지 않는다.

## 왜 필요한가

- 상담사 화면 개선 지시(2026-11-27)에 대체 숙소 카드마다 `이 숙소만 전송` 버튼이 있다. 상담사가 고객 상황에 맞는 한 곳만 권하고 싶어도 지금은 세 곳을 채워야만 보낼 수 있다.
- 프런트만으로는 할 수 없다. 서버가 3곳이 아닌 요청을 `400 INVALID_OFFER_REQUEST`로 거절한다.

## 지금 3곳이 강제되는 곳

DB는 바꿀 필요가 없다. `offer_items`의 제약은 `display_order BETWEEN 1 AND 3`이라 1~3건을 이미 허용한다(`V1__initial_business_schema.sql`). Flyway 수정·새 마이그레이션 없음.

## 제안하는 변경

- `POST /api/v1/cases/{caseId}/offers`의 `quoteIds`를 **1개 이상 3개 이하**로 받는다. URI·요청 필드 이름·응답·상태 코드·권한·멱등키 규칙은 그대로다.
- 그대로 유지하는 검사: 중복 없음, 서로 다른 숙소, 같은 사건의 최신 완료 검색·같은 기간 그룹, 재고·정원·통화·금액·기한, 현재 검증된 장애 숙박일, 대체 예약 진행 중일 때 차단.
- 새 제안이 이전 `ACTIVE` 제안을 `SUPERSEDED`로 바꾸는 규칙도 그대로다. **한 곳만 보내면 앞서 보낸 세 곳 제안은 선택할 수 없게 된다.** 화면이 전송 전에 이 점을 알려야 한다.
- 고객 선택(API-014)의 재검사를 "제안 항목 1~3건, 서로 다른 숙소"로 맞춘다.
- OFFER 메시지 본문을 개수에 맞게 쓴다("대체 숙소 N곳을 확인해 주세요…").
- 화면: 카드마다 `이 숙소만 전송`, 하단에 `추천 숙소 3곳 전체 전송`. 둘 다 같은 API를 쓰고 개수만 다르다.

## 대안

1. **지금 그대로 둔다(변경 없음).** 화면에는 `추천 숙소 3곳 전체 전송`만 있다. 현재 상태이며 시연 2는 그대로 통과한다.
2. **한 곳을 채팅 일반 메시지로 안내한다.** 서버 변경은 없지만 고객이 그 숙소를 "선택"할 수 없어 예약 흐름으로 이어지지 않는다. 권하지 않는다.
3. **이 제안(1~3곳).** 서버 검사 4곳, 메시지 본문, 프런트 2곳, 테스트·문서 수정.

## 일정에 대한 의견

11-28 기능 마감 전에는 대안 1을 유지하고, 승인되면 12-02 제출 전 별도 PR로 구현하는 것을 권한다. 제안·선택은 시연 2의 중심 경로라 마감 하루 전에 검사 조건을 바꾸면 리허설을 다시 해야 한다.
