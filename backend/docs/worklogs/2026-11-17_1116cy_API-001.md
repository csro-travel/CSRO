# 1116cy 작업 기록 — 개발 환경·공통 DB 초기화·API-001 예약 상세 조회

작성 기준: 2026-11-17  
작업 대상: 사용자 로컬 `CSRO` 프로젝트의 `1116cy` 브랜치  
주요 기술: Java 21 · Spring Boot 4.0.9 · Gradle 9.9.1 · PostgreSQL 18.7 · Docker Compose · Flyway

> 현재까지는 개발 환경을 준비하고, 공통 초기 스키마와 최소 개발용 예약 데이터를 적용한 뒤, API-001의 조회·소유권·역할·오류 처리 코드를 작성하고 관련 테스트를 실행한 단계다. 실제 Bearer 인증 연동, API-002 신고 처리, 상담 사건 C-001 생성, 전체 API 구현, 프론트 연동은 완료 범위에 포함하지 않는다.
>
> 이 기록은 전달된 SQL·Java 템플릿, 사용자가 공유한 실행 콘솔, 별도 검증 환경의 결과를 정리한 것이다. 사용자는 API-001 Java 파일을 전달본 그대로 사용했다고 확인했고, 이후 기본 테스트의 local 프로필 설정을 보완했다. 다만 사용자 Windows의 현재 파일 전체, 테스트 HTML/XML 보고서, `1116cy`의 로컬 커밋·원격 push·PR은 직접 확인하지 않았다.

## 1. 이번 작업의 목적과 도달한 단계

여행봄 개발을 시작할 수 있도록 로컬 실행 환경과 공통 DB 기반을 마련하고, 고객이 본인 예약의 계약 정보를 읽는 첫 API를 구현하는 것이 이번 작업의 목적이었다.

API-001의 대상은 `GET /api/v1/bookings/{bookingId}`다. 예약번호 YB-001을 조회하면 호텔, 체크인·체크아웃 날짜, 숙박일 수, 성인 수, 공급사 계약 상태, 원예약 금액, 활성 상담 사건 연결 정보를 고객용 JSON으로 반환한다. 이 조회 자체로 사건·Job·근거를 생성하거나 객실 제공 가능 여부를 확정하지 않는다.

## 3. 개발 환경 구성

개발 도구 설치는 PC 환경 준비이며 Git 브랜치에 저장되는 소스 변경과 구분한다. 아래는 이번 작업 세션의 준비·구현 기록이다. 사용자 작업 트리 전체 diff를 직접 수집한 것은 아니므로 실제 커밋 파일 수나 최종 변경 내역을 확정한 기록은 아니다.

### 3.1 사용자 환경에서 확인한 내용

- Windows에서 Java 21, Git, WSL, Docker를 준비했다.
- Spring Boot 4.0.9 애플리케이션을 Gradle 9.9.1로 시작했다.
- Docker Compose의 PostgreSQL 18.7 컨테이너가 healthy 상태가 됐다.
- Spring 애플리케이션과 PostgreSQL의 연결 성공을 확인했다.
- 이후 Flyway migration 적용과 예약 조회 SQL 실행까지 진행했다.
- 기본 Spring 프로젝트의 `BackendApplication`을 실행하고 `HelloController`의 `/hello` 응답을 사용자 브라우저에서 확인했다. `/hello` 확인은 서버 시작 확인용이며 예약 API·인증·DB 조회 검증과 구분한다.

### 3.2 전달된 Docker Compose 설정

| 항목 | 설정 |
| --- | --- |
| 서비스 | `postgres` |
| 이미지 | `postgres:18.7` |

## 4. 공통 업무 DB와 Flyway

### 4.1 초기 스키마의 범위

`V1__initial_business_schema.sql`은 공통 업무 테이블 21개, 외래키 46개, 명시적 인덱스 21개를 정의한다. 순환 참조를 처리하기 위해 테이블을 먼저 만든 뒤 외래키를 추가한다.

| 업무 영역 | 테이블 |
| --- | --- |
| 사용자·숙소·예약 | `users`, `hotels`, `bookings`, `booking_nights` |
| 위험·비동기 작업·근거 | `risk_assessments`, `jobs`, `evidence_records`, `agent_analyses`, `evidence_nights` |
| 상담 사건·신고·이력·채팅 | `cases`, `case_tasks`, `incident_reports`, `case_actions`, `chat_messages` |
| 대안 견적·제안·선택·예약·체크인 | `alternative_quotes`, `quote_rankings`, `offers`, `offer_items`, `alternative_selections`, `replacement_requests`, `checkin_confirmations` |

이 21개는 A/B팀이 합의된 물리 구조를 사용하기 위한 **공통 초기 스키마**다. B팀 API, Agent, ML, 대안 예약 처리까지 구현했다는 뜻이 아니다. Mock 공급사 테이블 4개는 이번 업무 DB 초기 스키마에서 제외했다.

Flyway 적용 환경에서는 업무 테이블 21개 외에 이력 관리용 `flyway_schema_history`가 존재할 수 있다. 업무 테이블 수와 Flyway 관리 테이블을 혼동하지 않는다.

### 4.2 Flyway 적용 구성

Gradle에는 Flyway starter와 PostgreSQL용 Flyway 모듈을 추가하는 안내를 전달했다.

```groovy
implementation 'org.springframework.boot:spring-boot-starter-flyway'
runtimeOnly 'org.flywaydb:flyway-database-postgresql'
```

local 프로필에서는 다음 위치를 사용한다.

```properties
spring.flyway.locations=classpath:db/migration,classpath:db/local
```

- `db/migration`: 공통 버전 migration `V1__initial_business_schema.sql`
- `db/local`: local 개발용 반복 migration `R__seed_yb001.sql`
- 기본 공통 경로와 local seed 경로를 구분해 샘플을 일반 실행 환경에 무조건 넣지 않도록 구성했다.
- 사용자 콘솔에서 V1과 R seed, 두 migration 적용이 확인됐다.

V1은 공동 작업 전 버전을 조정해야 하는 초기안이다. 다른 팀원이 이미 V1을 사용했는지 확인하고 공통 기준을 맞춰야 한다. 이미 적용한 versioned migration을 수정해 덮어쓰는 방식으로 후속 변경을 진행하지 않는다.

### 4.3 스키마 검증의 범위

별도 폐기 가능한 PostgreSQL 18.7 DB에서 다음 결과가 기록됐다.

- 빈 DB에 V1 SQL을 적용할 수 있었다.
- 업무 테이블 21개와 FK 46개가 생성됐다.
- local seed를 두 번 실행해도 같은 논리 레코드가 중복 생성되지 않았다.
- 예약·숙박일 샘플의 값이 기대와 일치했다.
- 동일 예약·숙박일 중복, 미확정 상태의 `UNAVAILABLE` 변경, 1 초과 위험 점수, 같은 예약의 두 번째 활성 사건, 다른 숙박일 근거를 채택 근거로 연결하는 시도가 거부됐다.
- 검증 과정에서 임시로 만든 자료는 롤백했고 기본 fixture가 유지됐다.

이는 **일부 핵심 제약이 특정 검증 사례에서 작동했다는 결과**다. 모든 비즈니스 불변식, 상태 전이, 승인 절차, 동시성, 재시도·멱등성, 실제 호텔 근거의 신뢰성을 전부 증명한 결과로 확대하지 않는다. DB 구조가 존재하는 것만으로 관련 서비스와 운영 절차가 완성되는 것도 아니다.

### 4.4 ERD 내보내기 SQL과 실행용 migration 구분

첨부된 `Copy of CS-ERD.sql`과 11월16일 복구본을 별도로 검토했다. 복구본에는 PostgreSQL이 지원하지 않는 백틱·컬럼 뒤 COMMENT 문법이 있어 별도 PostgreSQL18.7에서 첫 문장 구문 오류를 확인했다. 내보내기 파일에는 자동 ID 생성·다수 FK·UNIQUE·CHECK·인덱스가 설명에만 있거나 빠져 있었고, 숙박일과 근거 사이 잘못된 단일 FK도 있었다.

실행용 V1은 그 내보내기 파일의 기호만 바꾼 파일이 아니다. 현재 Notion의 업무 DB 상세 정의서5개 영역에 있는 PostgreSQL SQL문을 추출해 모든 테이블 생성 뒤 FK·인덱스를 추가하도록 구성했다. 이는 현재 업무 설계를 실제 DB 제약으로 옮긴 초기 migration이다. 이미 적용된 V1은 이번 주석·문서 정리에서 수정하지 않았다.

## 5. YB-001 개발용 데이터

### 5.1 적재한 내용

| 데이터 | 내용 |
| --- | --- |
| 가상 고객 | `demo-customer-001`, `demo-customer-002` 2명 |
| 가상 상담사 | `demo-counselor-001` 1명 |
| 숙소 | `HOTEL-001` / 제주 오션뷰 호텔 / `SIMULATED` |
| 앱 예약번호 | `YB-001` |
| 공급사 식별 | `MOCK_SUPPLIER` / `SUP-BOOK-001` |
| 예약 소유자 | `demo-customer-001`에 대응하는 사용자 |
| 공급사 계약 상태 | `CONFIRMED` |
| 숙박 | 2026-11-10 체크인, 2026-11-13 체크아웃, 3박 |
| 인원·객실 | 성인 2명, 객실 1개 |
| 원예약 총액 | 450,000 KRW |
| 숙박일별 초기 상태 | 11/10, 11/11, 11/12의 3개 행, 모두 `UNKNOWN` / `UNCONFIRMED` |
| 기준 가상 시각 | 2026-11-09, Asia/Seoul |
| 초기 사건·위험·근거 | seed에서 Case, 위험 평가, 호텔 근거, 검증된 숙박 불가를 생성하지 않음 |

사용자가 공유한 SQL 결과에서 `YB-001`, `CONFIRMED`, 11/10~11/13, 성인 2명, 450000, 숙박일 3개의 `UNKNOWN` / `UNCONFIRMED`를 확인했다.

`subject_key`는 사용자 매핑용 식별자다. 위의 `demo-*` 문자열은 로그인 토큰이나 비밀번호가 아니다. 앱 예약번호, DB 내부 PK, 공급사 예약번호도 각각 다른 식별자다.

### 5.2 더미 데이터가 의미하는 것

이번 seed는 **예약 계약과 API 응답 구조를 개발하기 위한 최소 가상 예제**다. 예약 `CONFIRMED`는 공급사의 계약 상태이며, 각 날짜의 객실 제공이 확인됐다는 뜻이 아니다. 숙박 가능 여부를 확인할 근거가 없으므로 숙박일은 `UNKNOWN` / `UNCONFIRMED`로 시작한다.

- 실제 고객·호텔·공급사 자료와 대조해 진실성을 검증한 데이터가 아니다.
- 실제 체크인 실패 또는 객실 제공 불가의 정답 라벨을 검증하지 않았다.
- 정상·실패·모호·충돌 등 데이터 분포의 대표성이나 규모를 검증하지 않았다.
- 대량 데이터 성능, 부하, 쿼리 실행 계획을 검증하기 위한 데이터셋이 아니다.
- Agent 분석 입력이나 ML 학습·평가 데이터셋으로 사용하지 않았다.
- 이전에 확보한 `HotelBookingDemandDatasets.zip`을 이번 seed에 혼합하거나 그 분포로 표본 추출하지 않았다. 이번 값은 문서의 가상 계약 예제를 고정 입력한 것이다.
- 모델 점수0.78을 실제 모델 추론 결과로 만들거나 risk_assessments에 적재하지 않았다. 플랫폼 확정 후 현장 예약 누락·중복 실패의 실제 라벨도 없다.
- 정상·첫날 장애·현장 신고의 세 가지 E2E를 모두 실행할 수 있는 데이터가 아니다. 현재 기본 seed는 신고·근거 확인 이전 상태다.
- 두 번째 고객과 상담사를 만들었다고 소유권·역할의 모든 조합을 seed 자체로 검증한 것은 아니다. 관련 검증은 별도 테스트 fixture로 수행했다.

따라서 “더미 데이터 완벽 검증”, “실제 장애 데이터 확보”, “ML 검증 데이터 완성”으로 기록하지 않는다. 계약 예제의 값과 일부 DB 제약을 확인한 수준으로 남긴다.

날짜는 가상 시나리오 기준으로 고정돼 현재 날짜에 따라 자동으로 바뀌지 않는다. seed는 없는 행을 추가하는 방식이며, 이미 처리 중인 YB-001의 상태를 매번 초기화하는 스크립트가 아니다.

## 6. API-001 구현 내용

### 6.1 요청과 조회 범위

```http
GET /api/v1/bookings/{bookingId}
Accept: application/json
```

인증 계약상 실제 클라이언트는 `Authorization: Bearer {accessToken}`을 사용해야 한다. 다만 이번 구현은 공통 인증 계층이 생성한 Servlet `Principal`을 받는 경계까지만 연결한다. Bearer 문자열을 검증해 Principal을 만드는 기능은 별도 작업이다.

요청 본문, 페이지네이션, 정렬, 필터는 없다. 예약 1건을 대상으로 하며 Booking·Hotel·예약 소유 고객·활성 Case를 읽는다.

### 6.2 파일별 역할

| 파일 | 역할 |
| --- | --- |
| `BookingDetailResponse.java` | 고객에게 공개할 예약 상세 DTO. 호텔·숙박·원가격·상담 연결 정보로 구성 |
| `BookingQueryRepository.java` | `JdbcClient`로 본인 예약과 활성 사건 조회. 예약번호와 인증 주체를 SQL 파라미터로 전달 |
| `BookingService.java` | Principal 확인 → 계정 조회 → 활성 여부 → CUSTOMER 역할 → 소유 예약 조회 순서로 처리 |
| `BookingController.java` | GET 경로와 Principal 수신, 성공 응답 및 `private, no-store` 캐시 헤더 반환 |
| `BookingExceptionHandler.java` | BookingController 범위의400·401·403·404·500을 Problem Details로 변환.400은 매핑만 준비 |
| `BookingApiIntegrationTest.java` | PostgreSQL과 독립 fixture를 사용하는 조회·권한·GET 안전성 테스트 |
| `BookingErrorResponseTest.java` | 이번 반영본의400 매핑과 안전한500 응답을 DB 없이 검증 |
| `BackendApplicationTests.java` | Spring 기본 애플리케이션 컨텍스트 시작 확인. 전체 테스트 실행을 위해 `@ActiveProfiles("local")`로 개발 DB 설정 사용 |

Service와 조회 Repository에 `@Transactional(readOnly = true)`를 적용했다. 이 설정만으로 모든 쓰기 방지가 증명되는 것은 아니며, 이번 테스트에서는 반복 GET 전후 업무 행의 실제 값도 비교했다.

### 6.3 고객용 성공 응답 계약 예시

아래 JSON은 YB-001 seed에 대응하는 **명세·DTO 기준 예시**다. 실제 Bearer로 사용자 브라우저에서 200 응답을 받았다는 실행 증거를 대신하지 않는다.

```json
{
  "bookingId": "YB-001",
  "hotel": {
    "hotelId": "HOTEL-001",
    "name": "제주 오션뷰 호텔"
  },
  "stay": {
    "checkInDate": "2026-11-10",
    "checkOutDate": "2026-11-13",
    "nights": 3,
    "adults": 2
  },
  "bookingStatus": "CONFIRMED",
  "originalPrice": {
    "amount": 450000,
    "currency": "KRW"
  },
  "support": {
    "activeCaseId": null,
    "needsAttention": false
  }
}
```

- 활성 사건은 `OPEN`, `IN_PROGRESS`, `WAITING`만 연결한다. `CLOSED`는 제외한다.
- 활성 사건이 있으면 `activeCaseId`를 반환하고 `needsAttention=true`로 표시한다.
- 상담 사건이 있어도 공급사 계약 상태 `CONFIRMED`를 자동으로 바꾸지 않는다.
- `needsAttention`은 상담 연결 표시이며 실제 숙박 불가 확정값이 아니다.
- 내부 위험 점수·모델 정보·호텔 원문·근거 payload·고객 내부 식별자는 고객 DTO에 포함하지 않는다.
- GET으로 사건, 재확인 Job, 신고 또는 근거를 생성하지 않는다.
- 박수는 예약의 체크아웃·체크인 날짜 차이로 계산한다. 실제 booking_nights 행이 전체 기간과 일치하는지 또는 객실 제공 상태가 검증됐는지를 API-001에서 추가 판정하지 않는다.

### 6.4 오류 응답

| HTTP | 서비스 코드 | 구현 범위 |
| --- | --- | --- |
| 401 | `UNAUTHENTICATED` | Principal 없음·미등록 계정·비활성 계정 등 |
| 403 | `FORBIDDEN_ROLE` | 활성 계정이지만 고객 역할이 아닌 경우 |
| 404 | `BOOKING_NOT_FOUND` | 없는 예약과 다른 고객의 예약에 같은 코드·설명 사용 |
| 500 | `INTERNAL_ERROR` | 예상하지 못한 오류를 일반 안내와 traceId로 반환 |
| 400 | `INVALID_BOOKING_ID` | 이번 검토 반영본에서 오류 응답 매핑과 단위 테스트를 보완. 최종 ID 형식 정책·실제 입력 검증은 미구현 |

오류는 `application/problem+json`을 사용하며 `type`, `title`, `status`, `detail`, 확장 필드 `code`, `traceId`를 제공한다. 응답에는 `Cache-Control: private, no-store`를 넣고 401에는 `WWW-Authenticate: Bearer`를 설정한다.

예상하지 못한 오류의 SQL·내부 예외 문구는 응답에 그대로 반환하지 않는다. traceId를 포함해 서버 로그와 연결할 수 있게 했다. 이는 응답 노출 제어의 범위이며 전체 로그 보안·보존 정책까지 완료한 작업은 아니다.

구체적으로500의 traceId는 서버 오류 로그에 함께 남긴다. 4xx 응답에도 traceId를 생성하지만 공통 요청 추적·중앙 로그 정책까지 연결한 것은 아니다.

### 6.5 인증 연결 전의 401

현재 인증이 Principal을 만들지 않는 상태에서 브라우저로 `http://localhost:8080/api/v1/bookings/YB-001`을 열면 401이 나오는 것이 코드상 의도된 동작이다. 사용자 식별자를 임의 헤더에 넣거나 `Bearer demo-customer-001`을 보내는 방식으로 로그인되도록 만들지 않았다.

테스트는 `MockMvc.request.principal(...)`로 시험용 주체를 주입한다. 여기서 본인 조회 200과 권한 오류를 통과한 것은 **애플리케이션 조회·인가 동작 검증**이다. 실제 토큰의 발급, 서명, 만료, 발급자·대상 검증 성공과 구분한다.

### 6.6 명세 대조 결론

조회 기능의 URL·JSON 계약·공급사 계약 상태·소유권·활성 사건 연결·GET 무변경·고객용 비노출·캐시·Controller 오류 응답은 검토한 구현 범위에서 명세와 일치한다. 전체 API 완료 판단에는 실제 공통 인증 연결과 최종 ID 입력 검증이 남는다. 400 오류 응답 매핑은 이번 검토에서 보완했다.

명세의 설명용 booking_id/status/original_amount를 그대로 물리 컬럼명으로 사용하지 않고 현재 ERD의 id/booking_code/supplier_status/original_total_amount/case_code와 API DTO를 매핑했다. 이 차이를 새로운 스키마 변경으로 취급하지 않았다.

상세 요구사항 대조표와 파일 책임은 `backend/docs/api/API-001.md`, 여러 API를 찾기 위한 진입점은 `backend/docs/api/README.md`에 정리했다. 코드의 API 표시와 커밋 작성자 이력은 별도 정보이며, 아직 만들어지지 않은 commit·PR을 이 기록의 작성 근거로 주장하지 않는다.

### 7.4 이 테스트가 보장하는 범위

반복 GET 검증은 정해진 테스트 요청 전후로 업무 테이블 21개 행의 값을 해시해 비교했다. 해당 시나리오에서 행 추가·수정·삭제가 없었다는 근거다. DB 시퀀스·접근 로그·외부 서비스·모든 동시 요청을 포함한 시스템 전체 부작용 검증은 아니다.

사용자 Windows에서는 기본 테스트의 local 프로필 보완 후 저장소 전체 `test` 명령의 성공을 확인했다. 기본 `contextLoads`는 애플리케이션 컨텍스트를 시작하는 테스트이며, API-001의 계약·인가 테스트나 실제 인증 E2E를 대체하지 않는다.

아래 항목은 이번 성공 결과로 완료 처리하지 않는다.

- 실제 HTTP 서버·브라우저·React·인증 발급자를 연결한 E2E
- 실제 Bearer 토큰 검증과 Spring Security 필터에서의 401/403 공통 응답
- 최종 bookingId 형식에 따른 실제 입력 검증400. 오류 매핑 단위 검증과 구분
- Gradle `check`·`build` 명령과 CI 파이프라인. 전체 `test` 명령 성공과 별도 검증 범위

### 7.5 이번 검토 반영본: API 표시와400 매핑 보완

Java7개 파일의 JavaDoc에 API-001 번호·명세 URL·파일 책임·공통 인증 미연결 범위를 표시했다. Controller 메소드에도 API 번호를 넣었고 JUnit DisplayName에 API-001과 검증 상황을 표시했다. API 인덱스와 파일별 명세 대조표도 추가했다.

새 반영본을 별도 Java21 / Spring Boot4.0.9 / PostgreSQL18.7 환경에서 재컴파일·재검증한 결과:

### 9.3 다음 업무 API: API-002

다음 A팀 연동 목표는 고객 신고를 받아 활성 사건을 생성·재사용하고 최초 처리 항목을 저장하는 API-002다. 신고·사건·최초 CaseTask·채팅·대기 Job 등 필요한 쓰기를 하나의 트랜잭션으로 묶는 구현과 검증이 남아 있다.

현재 seed에 C-001을 미리 넣지 않은 것은 누락이 아니라 신고 이전 초기 상태를 유지하기 위한 선택이다. 이번 API-001 GET에서 C-001이나 재확인 Job을 생성하지 않는다. B팀의 실제 사건 조회 통합에는 API-002 이후 생성되는 합의된 데이터가 필요하다.

B팀은 합의한 Case·숙박일·nextAction DTO와 별도의 “신고 후” 예시를 활용해 API-003/004 및 Agent 요청·응답 작업을 병행할 수 있다. 다만 그 예시와 API-001 초기 seed를 같은 완료 상태로 취급하지 않는다. A팀은 2명 공동 책임이며, 남은 작업 전체가 한 사람에게 배정됐다는 의미도 아니다.
