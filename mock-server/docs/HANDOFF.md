# API-026·027 Mock 서버 인계 — v0.1

추가된 API-028은 [검색 계약·실행·한계](API-028.md)를 따른다. 기존 API-026/027에 더해 같은 프로세스에서 가상 견적을 반환한다. Spring 견적 저장, 고객 제안, API-029 예약 실행은 아직 연결하지 않았다.

이번 작업은 A팀 Spring이 호출할 **독립 실행형 Mock 공급사·호텔 HTTP 서버**입니다. 계약 v0.1 검토안의 YB-001 정상 응답 본문과 주요 성공·대기·오류 분기를 개발 환경에서 확인하는 범위입니다.

## 구현 경계

| 포함 | 별도 작업 |
| --- | --- |
| FastAPI HTTP endpoint 2개 | Spring의 외부 API 호출 코드 |
| 개발용 내부 Bearer 서비스 토큰 확인 | 고객 로그인·상담사 권한·운영 인증 |
| 고정 가상 예약·숙박일 회신 fixture | 통합 데이터셋 생성·ML 학습·실제 모델 추론 |
| 공급사 계약 상태와 호텔 숙박일 주장 분리 | EvidenceRecord 저장과 BookingNight 사실 채택 |
| 호텔 정상·예약 미조회·대기·서비스 장애 분기 | 사건 생성·활성 사건 잠금·CaseTask·재시도 Worker |
| 로컬 PC의 `127.0.0.1:8001` 실행 | 공통 서버 배포·팀원 공용 네트워크 접근 |

DB 연결이나 테이블 생성이 없습니다. 업무 DB와 Mock DB의 물리 스키마를 새로 정하거나 기존 Flyway 파일을 바꾸는 작업도 없습니다. Spring 업무 DB는 Spring이 관리하며, 이 서버는 HTTP 응답으로 외부 시스템을 흉내 냅니다.

## HTTP 계약

| API | Method | URI |
| --- | --- | --- |
| API-026 공급사 기존 예약 조회 | GET | `/mock-supplier/v1/bookings/{supplierBookingId}` |
| API-027 호텔 숙박일별 재확인 | POST | `/mock-hotel/v1/reconfirmations` |

호출 방향은 **Spring → Mock 서버**입니다. 프론트에서 직접 호출하는 고객용 업무 API가 아닙니다. 서비스 요청에는 `Authorization: Bearer {internalServiceToken}`을 전달합니다.

응답 JSON은 API 명세의 camelCase 필드를 직접 반환합니다. Spring의 별도 공통 응답 DTO로 감싸는 계약을 추가하지 않습니다. `GET /healthz`는 실행 상태 확인, `GET /docs`는 개발용 Swagger 화면입니다. `healthz` 응답은 `status=ok`, `service=travel-mock`, `contractVersion=0.1`, `isSynthetic=true`입니다.

개발용 토큰 기본값은 `csro-local-mock-token`입니다. `MOCK_SERVICE_TOKEN` 환경 변수로 명시적으로 바꿀 수 있습니다. `.env.example`은 참고 파일이며 자동으로 읽지 않습니다. README의 PowerShell 환경 변수 설정을 사용합니다. 현재 프로세스의 개발용 서비스 토큰 검증이며, 사용자 인증 체계나 운영 보안 구성을 구현한 것은 아닙니다.

## YB-001 — 명세의 기준 사례

공급사 조회는 다음 매핑을 사용합니다.

```text
내부 예약: YB-001
공급사 예약: SUP-BOOK-001
호텔: HOTEL-001
숙박 기간: 2026-11-10 체크인 ~ 2026-11-13 체크아웃
인원·객실: 성인 2명, 객실 1개
공급사 계약: CONFIRMED
```

재확인 요청의 `reconfirmationRequestId` 예제는 `RECHECK-001`이며, `stayDates`는 `2026-11-10`, `2026-11-11`, `2026-11-12`입니다. 체크아웃 날짜는 제외합니다.

호텔의 `200 RESPONDED` 회신은 첫날 `UNAVAILABLE`, 둘째·셋째 날 `UNKNOWN`입니다. 응답의 `occurredAt`은 `2026-11-09T10:05:00+09:00`, `sentAt`은 `2026-11-09T10:06:00+09:00`입니다. 공급사 `updatedAt`은 `2026-11-09T09:00:00+09:00`입니다.

이는 고정 시연 시각입니다. 실행 PC의 현재 시각을 읽어 체크인 기간이 지났다는 이유로 실패시키거나 날짜를 자동 이동하는 방식이 아닙니다.

### Spring에서 이어서 해야 하는 일

1. 내부 예약의 공급사 예약 ID·호텔·전체 숙박일 매핑으로 API-026을 호출합니다.
2. 응답의 예약 식별자·기간·인원 등이 원예약과 맞는지 검증하고 공급사 원문·출처·수신 시각을 보존합니다.
3. 원래 3박의 숙박일로 API-027을 호출합니다.
4. 호텔 회신의 원문·발생 시각·수신 시각·예약과 날짜를 보존하고 검증합니다.
5. 호텔의 주장을 검토해 채택할 수 있을 때 **첫날만** 제공 불가로 반영합니다. 나머지 이틀은 미확인을 유지합니다.
6. 필요한 사건 생성·기존 활성 사건 연결·최초 작업 생성으로 이어 갑니다.

이 Mock 서버가 위 Spring 업무 처리를 대신 수행하지 않습니다. `reportedProvisionStatus=UNAVAILABLE`은 호텔의 주장이고, Spring의 `BookingNight.fulfillmentStatus`와 같은 저장 필드가 아닙니다. 첫날 불가를 곧바로 ‘오버부킹이 원인’으로 확정하는 응답도 아닙니다.

## 확장 fixture

YB-002~005는 주요 분기 확인을 위해 구현에서 추가하는 고정 사례입니다. 세부 ID·날짜 선택은 설계 v0.1의 YB-001 예제를 확장한 구현용 약속이며, 모든 값이 Notion에 이미 확정돼 있었다는 뜻이 아닙니다.

| 사례 | 공급사 조회 | 호텔 재확인 | 처리 의미 |
| --- | --- | --- | --- |
| YB-002 | `200 CONFIRMED` | `200`, 전 숙박일 `AVAILABLE` | 회신 정상·문제 없음 |
| YB-003 | `200 CONFIRMED` | `404 HOTEL_RESERVATION_NOT_FOUND` | 공급사는 확정했지만 호텔에서 예약 확인 실패 |
| YB-004 | `200 CONFIRMED` | `202 PENDING` | 요청은 접수했으나 호텔의 숙박일 회신은 아직 없음 |
| YB-005 | `503 SUPPLIER_UNAVAILABLE` | `503` 호텔 서비스 장애 | 외부 시스템 장애 분기 |

알 수 없는 공급사 예약 ID와 알려진 fixture의 호텔 미조회 상태는 다른 경우입니다. ID를 혼동해 오류가 난 결과를 특정 예약의 제공 불가 사실로 채택하지 않습니다.

실제 요청 ID 매핑은 다음과 같습니다. 모든 사례의 예약 기간은 `2026-11-10`~`2026-11-13`, 재확인 `stayDates`는 `11/10`, `11/11`, `11/12`로 같습니다.

| 내부 예약 | 공급사 예약 ID | 요청 호텔 ID | 회신 ID |
| --- | --- | --- | --- |
| YB-001 | `SUP-BOOK-001` | `HOTEL-001` | `RC-001` |
| YB-002 | `SUP-BOOK-002` | `HOTEL-002` | `RC-002` |
| YB-003 | `SUP-BOOK-003` | `HOTEL-003` | 오류 응답이므로 없음 |
| YB-004 | `SUP-BOOK-004` | `HOTEL-004` | `RC-004` |
| YB-005 | `SUP-BOOK-005` | `HOTEL-005` | 오류 응답이므로 없음 |

재확인 요청의 `reconfirmationRequestId`는 예를 들어 `RECHECK-002`처럼 지정하면 됩니다. 요청별 추적 ID이며, 공급사 예약 ID 대신 넣는 값이 아닙니다. YB-003의 호텔 미조회와 YB-005의 서비스 장애도 정확한 호텔·숙박일을 요청해야 해당 fixture 분기를 받습니다. 잘못된 호텔이나 기간을 보내면 입력 불일치 `422`가 먼저 반환됩니다.

매핑은 `app/fixtures.py`와 해당 자동 테스트를 함께 기준으로 봅니다. 표에 없는 임의의 예약을 실제 플랫폼 데이터처럼 추정해 사용하지 않습니다.

## 상태 코드를 해석하는 기준

| 응답 | 의미 | 자동 확정하면 안 되는 것 |
| --- | --- | --- |
| API-026 `200 CONFIRMED` | 공급사 계약상 예약 확정 조회 성공 | 호텔의 모든 객실 제공 가능 |
| API-027 `200` | 날짜별 호텔 회신을 받음 | 모든 날짜 정상 또는 검증된 사실 채택 |
| API-027 `202` | 요청 접수, 회신 대기 | 제공 가능/불가 중 어느 쪽도 확정 |
| `404` | 해당 시스템에서 예약 확인 실패 | 실제 계약 취소·객실 미제공·장애 원인 |
| `503` | 외부 서비스 사용 불가 | 고객 예약의 취소·미제공 |
| `401` | 내부 서비스 토큰 누락·불일치 | 예약의 업무 상태 변경 |
| `400` / `422` | 요청 형식·날짜·예약-호텔 매핑 등의 입력 문제 | 공급사/호텔의 실제 객실 상태 |

응답을 받았다는 사실과 고객의 숙박 문제를 검증했다는 사실을 분리합니다. 공급사 계약이 `CONFIRMED`인 채로 호텔의 첫날 제공 불가 회신이 존재할 수 있습니다.

## 비동기·응답 유실·원문 기록의 범위

`202 PENDING` fixture는 대기 분기를 확인하기 위한 응답입니다. 이 버전만 실행해서 시간이 지나면 자동으로 호텔이 회신하거나 사건이 갱신되는 것으로 간주하지 않습니다.

API-027 명세는 지연 회신의 우선 경로를 API-022 호텔 회신 이벤트로 설명합니다. 실제 API-022 콜백 송신·수신과 Worker의 재시도 한도·수동 인계는 별도 연결 작업입니다. 전용 재확인 조회 API를 임의로 새 계약처럼 추가해 설명하지 않습니다.

HTTP 요청 시 재확인 요청 ID를 전달하지만, 고정 fixture 서버만으로 재시작 이후의 영속 요청 원장이나 운영 수준 멱등성·동시성 보장을 구현했다고 보고하지 않습니다. 정확한 요청 추적·재시도 계약은 호출부 및 향후 서버 확장과 함께 검토합니다.

이 서버에 DB가 없으므로 업무 근거가 자동으로 보존되지 않습니다. Spring은 받은 응답·HTTP 상태·출처와 수신 시각을 업무 원문으로 저장해야 합니다.

## 로컬 실행과 팀 연결

각 팀원이 저장소를 받아 `mock-server`에서 설치·실행하면 자기 PC의 `http://127.0.0.1:8001`을 사용할 수 있습니다. 내 PC의 localhost 주소는 다른 팀원이 접근할 공통 서버 주소가 아닙니다.

현재 기본 실행은 `--host 127.0.0.1 --port 8001`입니다. 공통 통합 시연 서버·네트워크 노출·배포와 인증 설정을 완료한 상태로 설명하지 않습니다. Spring 설정에는 Mock base URL과 내부 서비스 토큰을 환경별 값으로 분리하는 연결 작업이 필요합니다.

## 공유·검증 기록

공유 단위는 프로젝트 최상위의 `mock-server` 폴더입니다. `1118cy`의 다른 미커밋 작업, 특히 통합 더미 데이터 생성기와 묶어 자동으로 커밋·푸시·병합하지 않습니다. 생성되는 `.venv`·캐시·개인 설정은 코드와 구분합니다.

자동 테스트 실행 명령은 다음과 같습니다.

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

실제 테스트 통과 건수·실행 환경은 제공되는 검증 기록을 기준으로 확인합니다. 클라우드에서 수행한 검증과 사용자의 Windows PC에서 직접 실행한 검증을 구분합니다. 문서의 실행 예제만으로 사용자 PC 검증 완료를 주장하지 않습니다.
