## API 개요

- <b>Method / URI:</b> <code>GET /mock-supplier/v1/bookings/{supplierBookingId}</code>
- <b>호출:</b> A팀 Spring → 가상 공급사 REST. 고객/상담사가 이 모의 공급사 URL을 직접 호출하지 않음.
- <b>목적:</b> 이미 예약된 YB-001이 공급사 계약상 정상 확정인지, 취소/변경이 있었는지 확인.
- <b>인증:</b> 개발용 내부 Bearer 서비스 인증.
- <b>자료:</b> YB-001과 공급사 예약번호의 매핑을 Mock fixtures에 고정.
- <b>실행 순서:</b> Spring 예약 매핑 조회 → Mock GET → 공급사 상태/기간 응답 → Spring 예약번호·기간 검증·원문 저장 → 필요 시 별도 호텔 재확인 027.

## HTTP 상태 코드별 의미

| HTTP | 코드 / 조건 |
| --- | --- |

## 설계 근거

1. <b>GET 사용:</b> 기존 예약 조회에는 새 예약이나 다른 상태 변경이 없고 동일 공급사 예약번호의 현재 계약상 상태를 읽기 때문이다.
2. <b>왜 공급사 ID로 조회하는가:</b> YB-001이라는 내부 식별자는 실 공급사의 고유 예약번호와 다를 수 있어 두 ID를 매핑해야 한다.
3. <b>왜 호텔 제공 상태를 넣지 않는가:</b> 계약상 확정과 실제 체크인 가능 여부는 별도 시스템/시점에서 판단할 수 있어 한 응답에서 섞으면 진실성 오판을 초래한다.
4. <b>왜 Spring에서 원문을 기록하는가:</b> 공급사 상태가 나중에 변경돼도 언제 어떤 계약 상태를 확인했는지 증빙하기 위함이다.
5. <b>왜 실패한 GET이 예약 취소를 의미하지 않는가:</b> 조회 실패·공급사 미등록·네트워크 장애는 서로 다른 원인이므로 사실 검증·수동 대응이 필요하다.

## A팀 구현 주의

- 원예약의 계약상 <code>CONFIRMED</code>는 객실 제공 가능 여부가 아니다. 호텔 재확인 API-027과 결과를 혼동하지 않는다.
- 공급사 자체 예약번호 SUP-BOOK-001과 내부 앱 예약번호 YB-001을 명확히 매핑한다.
- 공급사 조회 실패/미등록은 실제 예약 취소가 확인됐다는 뜻이 아니다. 근거 원본과 수신 시각을 저장한다.
