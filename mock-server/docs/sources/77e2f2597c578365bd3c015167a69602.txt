<quote>
<b>API-027 가상 호텔 숙박일별 재확인 \| 계약 v0.1 검토안</b>

예약 YB-001의 가상 공급사 계약 상태는 '확정'일 수 있지만 원래 호텔의 첫날 객실이 실제로 제공 불가일 수 있다. 이 API는 원래 호텔의 날짜별 회신을 시뮬레이션한다.
</quote>

## API 개요

- <b>Method / URI:</b> <code>POST /mock-hotel/v1/reconfirmations</code>
- <b>호출:</b> A팀 Spring → 가상 호텔 REST
- <b>목적:</b> 특정 공급사 예약·호텔에 대해 각 숙박일의 객실 제공 여부를 확인해 구조화된 원본 회신을 반환한다.
- <b>POST 설계 이유:</b> 호텔에 새 재확인 작업을 제출하고 그 요청의 결과를 기록한다. 신규 예약 실행이나 숙박일 상태의 무조건 변경은 하지 않는다.
- <b>인증:</b> 내부 Bearer 서비스 인증. 구조화 응답이라고 해서 자동 검증된 사실로 인정하지 않고 예약·숙박일·출처·상반 회신을 Spring에서 확인.

## 실제 실행 순서

```txt
① A팀 Spring: 공급사 조회 026에서 YB-001 예약 확정
       ↓
② Spring: 3박의 각 숙박일(11/10·11/11·11/12) 재확인 요청
       ↓
③ Mock 호텔: 11/10 제공 불가·나머지 2일 미확인 회신
       ↓
④ Spring: 원본·출처·시각 검증해 EvidenceRecord 저장
       ↓
⑤ 출처와 내용·충돌 검증 완료 시 첫날만 BookingNight 제공 불가
   11/11·12 = UNKNOWN 유지
       ↓
⑥ 실제 장애 대응 필요 → 활성 C-001 생성/연결
       ↓
호텔 무응답이면 객실 미제공 확정 X, 재시도 후 직접 전화 작업
```

## Request Header / Parameters

- <code>Authorization: Bearer {internalServiceToken}</code>
- <code>Content-Type: application/json</code>
- Path / Query: 없음.

## Request Body

```json
{
  "reconfirmationRequestId": "RECHECK-001",
  "supplierBookingId": "SUP-BOOK-001",
  "propertyId": "HOTEL-001",
  "stayDates": [
    "2026-11-10",
    "2026-11-11",
    "2026-11-12"
  ]
}
```

| 필드 | 타입 | 검증 |
| --- | --- | --- |
| reconfirmationRequestId | string | 재확인 요청 ID. 요청 재시도·상태 추적 |
| supplierBookingId | string | 이미 조회한 공급사 예약 ID. YB-001과 매핑 검증 |
| propertyId | string | 원래 예약 호텔 ID와 일치 |
| stayDates | date array | 중복 없는 원래 예약 숙박일 집합, 체크아웃 날짜 제외 |

<b>필드 의미:</b> <code>reportedProvisionStatus</code>는 호텔에서 주장한 숙박일 상태이며 Spring의 <code>BookingNight.fulfillmentStatus</code>와 구분한다. 요청 및 회신 원문·발생/수신 시각을 EvidenceRecord로 보존한 뒤에만 검증 규칙에 따라 상태를 변경한다. '제공 불가'를 바로 오버부킹 원인 확정으로 치환하지 않는다.

### 202 Accepted — 호텔 회신 지연

```json
{
  "reconfirmationRequestId": "RECHECK-001",
  "reconfirmationId": "RC-001",
  "status": "PENDING",
  "receivedAt": "2026-11-09T10:05:00+09:00"
}
```

모의 호텔이 요청만 받고 실제 회신이 늦는 경우 <code>202</code>와 <code>PENDING</code>을 반환할 수 있다. 뒤늦은 회신은 API-022 호텔 회신 이벤트로 전달하거나 작업자 재조회 규약을 별도로 정한다. 현재 목록에 전용 재확인 조회 API가 없으므로 <b>우선 022 콜백 경로</b>로 시뮬레이션한다. 실제 응답 시간 초과 시 재시도 한도·수동 인계는 Worker 계약에서 결정한다.

## 설계 근거

1. <b>계약과 실물 이행 분리:</b> API-026 '예약 확정'과 API-027 11/10 '제공 불가'를 별도 사실로 두어 사건 탐지의 핵심 경계 조건을 검증한다.
2. <b>숙박일별 응답:</b> 3박 중 하루만 문제가 있을 때 전체 3박 제공 불가로 덮어쓰지 않게 한다.
3. <b>POST 작업 모델:</b> 호텔에 재확인 작업을 요청하는 것과 예약 상태를 조회하는 것이 다르며, 재확인 요청/결과 기록·비동기 대응이 가능하다.
4. <b>202·503 구분:</b> 요청이 접수됐지만 응답 대기 중인 상태와 서비스 자체가 오류 난 상태를 구별해 상담사 작업 기한을 관리한다.
5. <b>모의 호텔도 원문 보존:</b> 나중에 '이제 제공 가능'이라는 새 회신이 와도 이전 증빙을 덮어쓰지 않고 정정 근거를 검토한다.
6. <b>고객 신고와 사실 확인 분리:</b> 호텔이 404를 반환했다고 고객 신고가 곧 사실로 확정되는 것은 아니다.

## A·B팀 구현 주의

- 호텔의 날짜별 응답은 <code>reportedProvisionStatus</code>라는 <b>주장</b>이다. 출처·예약·기간 확인 후에만 검증된 <code>BookingNight</code> 상태로 반영한다.
- 3박 중 11/10이 불가라도 11/11·11/12는 자동으로 불가/가능을 확정하지 않는다.
- <code>202 PENDING</code>은 정상 접수 후 회신 대기, <code>503</code>은 서비스 장애로 구분한다. 자연어 원문이 필요하면 B팀 Agent API-024를 사용한다.
