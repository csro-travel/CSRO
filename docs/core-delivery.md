# 금요일 시연의 필수 흐름과 남은 결정

목표일은 **2026-11-27(금)**이다. 이 문서는 일정 제안과 코드에서 확인한 범위를 기록하며, 팀원의 담당·일정 확정을 대신하지 않는다.

기준은 [Notion E2E](https://app.notion.com/p/cfb2f2597c57821bb16e014bdc22c147)의 YB-001 전체 3박 고객 구제 흐름이다. 모든 예약·견적·입실 기록은 시연용 가상 데이터다.

## 완료 기준

위험 점검 → 공급사·호텔 근거 확인 → 사건 1건 → 같은 기간의 후보 3개 → 상담사가 고객에게 제안 → 고객이 실제 발송된 후보 선택 → 상담사가 가상 예약 실행 → 입실·필수 후속 업무 확인 → 사건 종료.

다음 보호 조건도 함께 통과해야 한다.

- 위험 점수만으로 장애를 확정하지 않는다. 나머지 미확인 숙박일은 그대로 구분한다.
- 선택만으로 예약을 확정하거나 예약 성공만으로 사건을 종료하지 않는다.
- 예약 응답 유실 시 같은 요청 ID로 결과를 조회한다. 중복 클릭으로 예약을 두 번 생성하지 않는다.
- 전 기간을 보장하지 못하거나 원예약 후속 업무가 미완료이면 종료를 차단한다.

PR #17은 독립적인 검색 Agent와 후보 비교 화면을 추가했다. `1124cy-core-flow`는 별도의 결정적 Mock 견적을 Spring에 저장하고 제안·선택·가상 예약 결과 처리까지 연결하는 브랜치다. main 반영 여부는 해당 PR 병합과 구분한다. 입실·원예약 처리 완료·종료는 남아 있다. 기존 화면을 활용하되, 실시간 Google/Airbnb 후보를 설계의 가상 공급사 확정 견적처럼 저장하지 않는다.

## 구현 전에 필요한 최소 결정

API-009/010은 [사용자 승인 최소 계약](../backend/docs/api/API-009-010-PROPOSAL.md)으로, API-013/014는 [제안·선택 승인 계약](../backend/docs/api/API-013-014-PROPOSAL.md)으로, API-015/016과 별도 Mock 예약 저장소는 [예약 승인 계약](../backend/docs/api/API-015-016-PROPOSAL.md)으로 구현한다. Notion 팀 전체의 설계 승인 상태를 변경한 것은 아니다. 상세 JSON·오류·멱등성이 미작성인 후속 API는 구현 전에 구체적으로 합의한다. 목록에 URI가 있다는 이유로 계약 확정으로 취급하지 않는다.

[API-029](https://app.notion.com/p/a862f2597c5783e1b7af81b43a757fb0)는 별도 Mock DB 안에서 전 숙박일 재고 차감·예약·요청 결과를 하나의 트랜잭션으로 저장하도록 요구한다. 승인한 선택적 `compose.mock.yaml`과 Mock 전용 마이그레이션으로 구현하며 기본 업무 DB Compose는 유지한다. 업무 DB 재사용이나 고정 성공 응답으로 이 조건을 대체하지 않는다. 입실·종료 등 후속 공통 계약 변경에도 [AGENTS.md](../AGENTS.md)의 사전 영향 설명·승인 기준을 적용한다.

고급 추천 가중치 실험, 새 ML 모델 학습, 실제 결제·환불·원예약 자동 취소, 실공급사 운영 연동은 이번 필수 흐름을 막지 않도록 후순위로 둔다.
