# 금요일 시연의 필수 흐름과 남은 결정

목표일은 **2026-11-27(금)**이다. 이 문서는 일정 제안과 코드에서 확인한 범위를 기록하며, 팀원의 담당·일정 확정을 대신하지 않는다.

기준은 [Notion E2E](https://app.notion.com/p/cfb2f2597c57821bb16e014bdc22c147)의 YB-001 전체 3박 고객 구제 흐름이다. 모든 예약·견적·입실 기록은 시연용 가상 데이터다. 현재 적용 기준은 API-002·API-024가 포함된 `1125cy-api024/db3b15f`이며, 입실·업무·종료는 과거 사용자 승인 `1124cy-core-flow/f5add12`의 최소 범위를 보존해 연결한다.

## 완료 기준

위험 점검 → 공급사·호텔 근거 확인 → 사건 1건 → 같은 기간의 후보 3개 → 상담사가 고객에게 제안 → 고객이 실제 발송된 후보 선택 → 상담사가 가상 예약 실행 → 입실·필수 후속 업무 확인 → 사건 종료.

다음 보호 조건도 함께 통과해야 한다.

- 위험 점수만으로 장애를 확정하지 않는다. 나머지 미확인 숙박일은 그대로 구분한다.
- 선택만으로 예약을 확정하거나 예약 성공만으로 사건을 종료하지 않는다.
- 예약 응답 유실 시 같은 요청 ID로 결과를 조회한다. 중복 클릭으로 예약을 두 번 생성하지 않는다.
- 전 기간을 보장하지 못하거나 원예약 후속 업무와 VERIFY_HOTEL을 포함한 필수 업무가 미완료이면 종료를 차단한다.
- 같은 원예약 전체에 PENDING/RUNNING/WAITING 상태의 RECHECK Job이 남으면 RECHECK_PENDING으로 종료를 막는다. 다른 소유 작업을 종료를 위해 임의 완료·취소하지 않는다.

PR #17은 독립적인 검색 Agent와 후보 비교 화면을 추가했다. PR #18은 `6b3d386`으로 main에 병합되어 결정적 Mock 견적의 Spring 저장·제안·선택·가상 예약과 API-002를 반영했다. 이번에는 사용자의 계속 진행 지시에 따라 보류했던 입실·원예약 후속 완료·종료 구현을 현재 코드에 맞춰 연결한다. 과거 ZIP의 검증 기록을 이번 코드의 통과 결과로 사용하지 않는다. 실시간 Google/Airbnb 후보를 설계의 가상 공급사 확정 견적처럼 저장하지 않는다.

## 적용한 최소 계약과 범위

API-009/010은 [사용자 승인 최소 계약](../backend/docs/api/API-009-010-PROPOSAL.md)으로, API-013/014는 [제안·선택 승인 계약](../backend/docs/api/API-013-014-PROPOSAL.md)으로, API-015/016과 별도 Mock 예약 저장소는 [예약 승인 계약](../backend/docs/api/API-015-016-PROPOSAL.md)으로 구현한다. 입실·업무·종료는 [과거 사용자 승인 최소 계약](../backend/docs/api/API-008-017-018-PROPOSAL.md)을 유지해 적용한다. Notion 팀 전체의 설계 승인 상태를 변경한 것은 아니다. 상세 JSON·오류·멱등성이 미작성인 후속 API는 구현 전에 구체적으로 합의한다. 목록에 URI가 있다는 이유로 계약 확정으로 취급하지 않는다.

[API-029](https://app.notion.com/p/a862f2597c5783e1b7af81b43a757fb0)는 별도 Mock DB 안에서 전 숙박일 재고 차감·예약·요청 결과를 하나의 트랜잭션으로 저장하도록 요구한다. 승인한 선택적 `compose.mock.yaml`과 Mock 전용 마이그레이션으로 구현하며 기본 업무 DB Compose는 유지한다. 업무 DB 재사용이나 고정 성공 응답으로 이 조건을 대체하지 않는다. 입실·종료에서도 기존 업무 DB·Mock 소유권·HTTP 경계를 유지하며, 승인 범위 밖 공통 계약 변경에는 [AGENTS.md](../AGENTS.md)의 기준을 적용한다.

고급 추천 가중치 실험, 새 ML 모델 학습, 실제 결제·환불·원예약 자동 취소, 실공급사 운영 연동은 이번 필수 흐름을 막지 않도록 후순위로 둔다.

## 전체 시연 실행과 인계

저장소 루트에서 `py tools\demo\core-demo.py`를 실행한다. 기본 포트가 사용 중이면 비어 있는 포트를 확인한 후 `--mock-port 18027 --agent-port 18025 --ml-port 18023`처럼 명시한다. 실행기는 기존 프로세스나 DB를 종료·재사용하지 않으며 자기가 시작한 격리 서비스만 관리한다.

실제 저장 ML 모델·합성 관측으로 평가하고 기존 `MAX_OBSERVED_RECALL`을 명시해 Mock 재확인·사건을 준비한다. 모델·특징값·임계값을 고치거나 점수를 고정한 성공 응답으로 대체하지 않는다. 고객 신고 주소는 `http://127.0.0.1:3101/customer/bookings/YB-001`이며, 새 신고는 기존 활성 사건을 재사용한다. API-024는 저장 자연어 원문 한 건의 별도 수동 분석 경로로 유지한다.

예약 확정 뒤 실행기에 `arrive`를 입력해 가상 숙박일로 전진하고 고객 본인이 입실을 확인한다. 상담사는 CONTACT_CUSTOMER·VERIFY_HOTEL·ORIGINAL_FOLLOWUP 등 화면에 남은 모든 필수 업무를 실제 확인 내용으로 완료한 뒤 부족 조건을 다시 읽고 종료한다. 고정된 업무 개수나 예약 성공만으로 종료를 대신하지 않는다.

이번 코드의 Linux 집중 검사·브라우저·실행기·전체 대표 시연은 통과했다. 실제 결과와 미검증 범위는 [RESOLUTION-DEMO.md](../backend/docs/api/RESOLUTION-DEMO.md)에 기록했다. 이번 단계의 Windows와 원격 CI 실행은 남아 있다.
